> 2026 수원고교 피지컬 AI 메이커톤용. 작성 2026-10-30 KST.
> v1(`최종_산출물.md`)의 '센서 → 판단 → LED' 5개를 실제 대형 해커톤 수상작 23건의 설계 패턴으로 고도화했다. Claude와 GPT-6-Astra(max)가 각자 수상작을 조사한 뒤 2라운드 토론(4·5라운드)을 거쳐 합의한 결과다. 민원 데이터 근거의 상세는 v1 §2와 `data/evidence_summary.md`에 있다.

## 0. 결론
**v1의 공통 약점은 '알리고 끝난다'는 것이었다.** v2는 다섯 아이디어를 '감지 → AI 판단 → 다음 행동 제안 → 승인 → 물리 안내 → 결과 확인'으로 설계했다. 결과 확인의 근거는 구분한다. 통로 복구·수거·배수·소음 변화는 센서로 관측하고, 이용자의 도착·탑승은 당사자 확인을 함께 쓰며 센서만으로 확정하지 않는다.

### 0-1. 숙련팀 추천: 막힌 길부터 버스 탑승까지

**핵심 문제**: 통로가 잠깐 열렸다는 사실과 사람이 목적지까지 이동했다는 사실은 다르다. 도움 요청을 받았다는 사실과 실제 탑승 완료도 다르다. 이 차이를 두 장치가 같은 이동 건으로 추적한다.

| 구분 | 설계 |
|---|---|
| 보도 노드 | A/B 통로 관측, LED·서보 화살표, 이동 확인 입력 |
| 정류장 노드 | 승차 요청·수락 입력, 정차면 점유 관측과 담당자 현장 확인, 통과 감지, 당사자 탑승 확인 |
| 노트북 | 두 노드의 최신 관측을 관리하고 이동 상태 전이를 확정하는 단일 호스트. Command Code 판단·제안, 승인 화면과 결과 기록 |
| 범위 밖 | 자유 경로 탐색·TinyML·세 번째 착용 노드·실시간 버스 API. 통합 시연의 필수 기능으로 넣지 않는다 |

**이동 상태(구현할 설계)**:
요청 → 경로 제안 → 승인 → 이동 확인 → 승차 요청 → 수락 → 정차면 확보 → 통과·당사자 확인 → 완료.
재차단·센서 오류·노드 보고 끊김이면 보류한다. 재계획은 사람이 승인한 사전 지정 경로 선택으로 제한한다. 경고 단계, 경로 선택, 이동 완료 상태는 서로 다른 값으로 관리하며 노트북 호스트만 상태 전이를 확정한다. 통과 감지만으로 당사자의 탑승을 확정하지 않는다.

**AI와 제어의 경계**:
- 피코 로컬 규칙: 즉시 점유·센서 오류 표시. 네트워크 응답을 기다려 안전 반응을 결정하지 않는다.
- 노트북 상태 기계: 경로 후보·이동 단계·완료를 확정한다. 사전 지정 경로와 센서 관측, 사람이 승인한 정보만 쓴다.
- `typesafe/jev`: 비식별 센서 요약의 상태 분류. 확률 0.80 기준은 초기 설정이며 정확도 보장이 아니다. 보류 비율과 오분류를 측정해 정한다.
- LLM(chat): 아래 언어 계층. 경로 변경·음성 안내는 사람 승인 뒤 실행하고, 상황이 달라졌으면 제안을 폐기한다.

**LLM의 역할: 사람의 말과 시스템 상태를 잇는 언어 계층** (7라운드, GPT 수정 채택)
판단과 제어는 규칙과 상태 기계가 맡는다. LLM은 규칙이나 템플릿으로 다루기 어려운 **사람의 자유 문장**을 맡는다. "규칙으로 되지 않느냐"는 질문에는 같은 문장 세트로 템플릿 기준선과 비교한 결과로 답한다.

| 우선순위 | 역할 | 입력 → 출력 | 상태 |
|---|---|---|---|
| 1 | 현장 문장 구조화 | 관리인 메모·이용자 요청·운전자 응답 → `{출처, 원문, 대상 노드, 시간, 요구 조건}` 후보 | 새 구현 |
| 2 | 점검 요청서 초안 | 센서 기록·승인된 메모 → 관리자용 300자 초안, 위반 판단 금지, 자동 제출 없음 | 센서 기록 입력은 구현됨(`/report`), 실호출 확인(2026-10-31, 5.0초·201자). 메모 입력은 새 구현 |
| 3 | 다음 행동 제안 | 노드 상태와 승인된 구조화 정보 → 허용 행동 하나·이유·안내 문장 | 부분 구현(`AGENT=1`: 노드 상태 → 안내 문장·대상 노드 단계 상향 제안), 실호출 확인(제안 생성 7.2초). 구조화 정보 입력과 경로 행동 목록은 새 구현 |

- 예 1: 관리인이 "A 쪽 자재는 6시까지 못 치워요"라고 입력한다.
  - LLM은 `{출처: 관리인, 대상: A, 조건: 점유 지속, 시각: 18:00, 원문}` 후보만 만든다. "A 사용 불가"를 확정하지 않는다.
  - 규칙이 등록된 노드인지, 원문에 있는 내용인지 검증하고, 사람이 승인하면 상태 기계가 18:00까지 A를 경로 후보에서 뺀다.
  - 센서 관측과 메모가 어긋나면 보류한다.
- 예 2: 이용자가 "휠체어라 턱 있는 길은 못 가요"라고 입력한다.
  - LLM은 `단차 없음` 조건을 추출한다.
  - 상태 기계는 사전 지정 경로 중 단차 없는 경로만 후보로 둔다. LLM이 새 경로를 만들지 않는다.
- 대상별 안내(이용자·운전자·관리인)는 템플릿으로 시작한다. '불법' 민원 유형 분류는 위반 판단과 같은 효과라서 하지 않는다.
- **LLM이 하지 않는 것**: 통로의 존재·통행 가능 판단, 이동·탑승 완료 선언, 실시간 안전 반응, 장치 직접 구동, 위반·책임 판단
- **오독·주입 대비**: JSON 형식이 맞아도 부정·조건·시간을 잘못 읽거나 문장 속 지시를 따를 수 있다. 스키마 검증과 별도로 허용 필드와 원문을 대조하고, 사람이 승인한 뒤에만 반영한다.
- **개인정보**:
  - 자유 문장에는 장애 관련 요구·위치·이동 시각이 들어간다. 보내기 전에 필요한 필드만 남기고 저장 범위를 정한다.
  - chat 요청에는 `x-cmd-zdr: 1`을 붙인다. [Command Code 문서](https://commandcode.ai/docs/provider)에 따르면 이 헤더를 붙인 요청은 ZDR 업스트림으로만 처리되고, ZDR 업스트림이 없으면 422로 거부된다.
  - `typesafe/jev`는 ZDR 업스트림이 없으므로 자유 문장을 보내지 않는다.
  - `deepseek/deepseek-v4.1-flash`는 이 헤더를 붙인 요청에 HTTP 200으로 응답했다(2026-10-31 실호출). 모델을 바꾸면 다시 확인하고, 422가 나면 이 기능은 수동 입력으로 대체한다.
- **실패 처리**: 키 만료·시간 초과·늦은 응답이면 규칙과 수동 운용을 유지한다. 늦게 도착한 LLM 결과는 현재 상태 버전과 맞지 않으면 적용하지 않는다.

**90초 시연에서 증명할 장면**:
1. A 차단으로 B 경로를 제안했지만 승인 전에 B까지 막힘 → 낡은 제안 폐기·도움 요청. 억지 우회로를 만들지 않는다.
2. 통로 복구 후 이동·승차 요청 → 운전자가 수락해도 미완료 유지 → 정차면 관측·담당자 현장 확인, 통과 감지·당사자 확인 후 완료.
3. 한 노드의 보고를 끊음 → 그 구간을 ‘비어 있음’으로 취급하지 않고 보류 표시. 다른 노드의 로컬 감지는 계속 동작.

**12시간 작업량(계획)**: 계약·상태 정의 1h / 두 노드 단독 동작 3h / 상태 전이·승인 연동 3h / 반복 측정·재차단·보고 끊김·중복 입력 검증 2h / 발표 준비 1h / 통합 지연 예비 2h. 3인이라면 하드웨어·보정 / 펌웨어·로컬 제어 / 상태 관리·Command Code로 나누고 통합 검증은 함께 한다. Command Code 담당은 두 노드 단독 동작 3h 동안 언어 계층(문장 구조화·검증)을 병렬로 만든다. 평가 문장 세트는 프롬프트를 쓰지 않는 팀원이 미리 만든다. 이는 구현 보장이 아닌 작업 계획이다.

**측정할 지표(결과 아님)**: 차단·센서 오류 때의 오안내, 수락만으로 완료되는 허위 완료, 상태 변경 후 낡은 제안 실행, 관측→로컬 표시·클라우드 제안의 지연을 분리해 기록한다. 단순 임계값만 쓰는 기준선과 비교하고 실제 측정 전에는 정확도·지연 수치를 적지 않는다.

**LLM 평가(결과 아님)**:
- 프롬프트 작성에 쓰지 않은 문장 세트에 정답을 붙인다. 부정, 조건, 시간, 상충 제보, 미등록 노드, 지시 주입 문장을 포함한다.
- LLM과 템플릿·키워드 기준선을 같은 입출력 계약으로 비교한다.
- 지표: 핵심 조건 누락·반전, 근거 없는 필드 추가, 거부해야 할 요청의 수용, 사람의 수정 부담, 승인 가능한 후보가 나올 때까지의 지연
- 30문장 정도는 스모크 시험으로만 본다.

**준비된 것과 새 구현을 구분**: 스타터에는 통신·프로필·승인·명령 ID와 chat 제안·요청서 초안이 있다. 이동 건별 상태 전이, 두 노드 인계, 경로별 물리 동작, 완료 검증, 자유 문장 입력·구조화·원문 대조 검증, ZDR 헤더 적용은 이 통합안의 새 구현 범위다. 아직 완성된 기능이나 시연 검증 결과가 아니다. Command Code 실호출로는 기본 기능(jev 판단, chat 제안, 요청서 초안)만 확인했다(§5).

**나머지 세 후보의 기술적 승부처**: 공동 수거는 배출 분산과 센서 기반 완료, 배수는 동일 조건 재실험, 소음은 배경 변화와 조치 효과 분리다. RP2040의 [Edge Impulse C++ 배포](https://docs.edgeimpulse.com/hardware/deployments/run-cpp-rpi-rp2040.md)는 공식 지원되지만, 파형 수집·학습 데이터·메모리를 확인하기 전에는 TinyML을 필수 범위로 넣지 않는다.

## 2. 수상 패턴 → 설계 원칙
1. **한 사람의 이야기**로 시작한다(Argus, ATTI, REWEBA). 예: '휠체어로 역 앞 연결로를 지나는 사람', '두 배출장소를 맡은 관리인'
2. **출력은 다음 행동을 바꾼다**(FarmX, SmartScale, Shepherd). 빨간불로 끝내지 않고 통로·배출구·작업 순서를 정한다.
3. **조치 결과의 증거를 구분한다**. 시설 상태·적재량·배수·소음 변화는 센서로 다시 측정한다. 이용자의 도착은 당사자 버튼으로 확인하며, 통합 승차 완료는 통과 감지와 당사자 확인을 모두 요구한다. 버튼 입력을 센서가 확인한 사실처럼 표현하지 않는다.
4. **측정·판단·설명의 역할을 나눈다**. 피코는 센서 요약, jev는 상황 판단(확률), chat LLM은 허용 목록 안의 다음 행동 하나와 이유를 제안한다.
5. **불확실하면 멈춘다**(Peel의 '확인 불가'). 확률 0.80 미만은 review, 센서 오류는 파랑, 낡은 제안은 폐기한다.
6. **안전 반응은 기기에서, AI는 막지 않는 보조로**(Shepherd). 네트워크가 끊겨도 로컬 규칙으로 동작한다.
7. **사람이 승인한다**. 상태 LED는 자동으로 표시하되, 경로 변경·chat의 행동 실행·음성 안내는 승인 뒤에만 한다. 이는 목표 설계이며 아이디어별 동작은 피코 코드에 추가해야 한다.
8. **같은 센서로 더 큰 이야기**(Smart Hiking Stick, Ice Savers, FloodNet). 비싼 부품 대신 기본 센서의 결합 방식을 바꾼다.

## 4. 아이디어 상세
아래는 아이디어별 목표 설계다. 중계 서버의 `typesafe/jev` 프로필과 공통 승인·통신은 준비되어 있다. 센서 요약·완료 검증·경로별 장치 동작은 기본 예제 `access_space`에서 아이디어에 맞게 구현해야 한다. 상태 LED는 자동, chat LLM(`deepseek/deepseek-v4.1-flash`)의 행동·경로 변경·음성 안내는 승인 뒤 실행하는 구조로 설계한다. 세부 단계는 §0-1과 §5를 구분해 읽는다.

### ① 막힌 길을 다시 잇는 접근성 경로 안내 (`route_guide`) 27점 (근거4 구현4 피지컬5 시연5 SDG5 경쟁력4)
- **이야기**: 휠체어 이용자가 역 앞 연결로에서 적치물·불법 주차를 만난다. 지금은 '막혔다'는 사실조차 아무도 알려 주지 않는다. 이 장치는 쓸 수 있는 다른 통로를 알려 주고, 관리인에게는 어느 통로를 복구해야 하는지 알린다.
- **근거**: '인도 불법' 2023~25, '장애인 전용구역' 2021~25(E2), 저녁·밤 시민 신고 의존(§3)
- **참고 수상작**: Shepherd(행동 유도), Argus(이용자 부담 감소), Peel(판단 보류), Project Sidewalk(접근성 지도)
- **하드웨어(피코 1대)**: HC-SR04 2개(A/B 통로의 좁은 목), 안내 요청 버튼, 도착 버튼, 통로별 LED, SG90 방향 화살표. 키트 외 약 1.2~2.1만원[추정]
- **AI**
  - jev: `route_a / route_b / ask_helper / review`. 입력은 A/B 점유 지속, 센서 오류, 요청, 사전 점검한 단차 정보다. 단차 있는 통로는 고를 수 없다.
  - chat 제안: 예) "A 통로가 25초째 막혀 있습니다. B로 안내하고 관리인에게 A 복구를 요청하세요". 승인 후 화살표 이동과 음성(선택)이 나간다.
  - 완료 확인: 도착 버튼은 당사자의 도착 확인, A 초음파의 비점유 관측은 관측 지점의 통로 복구로 기록한다. 서로 다른 증거이며 이 단독안의 도착은 센서로 증명한 이동이 아니다.
- **시연할 장면**: 심사위원이 A에 장난감 차를 놓으면 차단 LED가 자동으로 바뀐다. 사람이 B 경로 제안을 승인하면 화살표가 움직인다. B도 막히면 낡은 제안을 취소하고 도움 요청으로 전환한다. 차를 치우면 관측 지점의 복구가 기록된다. 인터넷을 끊었을 때는 로컬 상태 표시와 파란 불을 보여 주며, AI 경로 안내가 계속된다고 주장하지 않는다.
- **선택 확장**: 두 번째 피코로 진동 지팡이 노드를 만든다(HC-SR04 + 진동모터). 시각장애인 단독 보행 안전장치라고는 말하지 않는다.
- **리스크**: 초음파는 통로 전체를 보지 못하므로 관측 지점을 좁은 목으로 한정한다. 실제 길에서는 현장 재점검이 필요하다.

### ② 배출 분산과 수거 완료를 검증하는 공동 수거 스테이션 (`collect_station`) 26점 (3/4/5/5/5/4)
- **이야기**: 두 배출장소를 맡은 관리인이 한쪽 넘침과 통로 적치를 동시에 만난다.
- **근거**: 청소 담당 부서 접수 2015~2023 연 3,379~4,185건(간접), '쓰레기 투기' df 2,520(2025)
- **참고 수상작**: SmartScale·FarmX(판단 → 선택 변경), H.E.A.T.M.A.P.(장소별 비교)
- **하드웨어**: HC-SR04 3개(A/B 적재, 접근부), SG90 분기 날개(종이공을 A/B로 유도), RGB, 수거 완료 버튼. 키트 외 약 1.4~2.5만원[추정]
- **AI**
  - jev: `use_a / use_b / hold / review` + 보조 질문 `access_blocked`, `collection_needed`
  - chat 제안: 관리인 작업 순서. 예) "접근부 정리 → A 수거"
  - 완료 확인: 버튼 + 센서가 빈 통을 연속으로 확인해야 완료다. 버튼만 누르면 작업이 사라지지 않는다.
- **놀라운 장면**: A를 채우면 종이공이 B로 간다. 접근부에 상자를 두면 배출을 보류한다. 아무것도 치우지 않고 완료를 누르면 '미완료'가 그대로 남는다.

### ③ 요청부터 탑승까지 이어지는 승차 인계 보드 (`boarding_handoff`) 25점 (4/4/4/4/5/4)
- **이야기**: 교통약자가 정류장에서 도움을 요청해도 운전자가 봤는지 모른다. 요청이 사람 사이에서 사라진다.
- **근거**: '버스 정류장'(2020·2023·2024), '버스정류소 불법' 2023~25, 대중교통과 2015~2025 연 4~6천 건
- **참고 수상작**: REWEBA(전문가 인계), HeadHome(당사자 + 보호자 두 축), Argus
- **하드웨어**: 요청·수락·도착 모사·탑승 확인 버튼, HC-SR04(정차면), 적외선 센서(통과), RGB, SG90 표지, 진동모터(수락 알림). 키트 외 약 1.4~2.6만원[추정]
- **AI**
  - jev: `idle / clear_space / offer_help / both / review`
  - chat 제안: 요청자·운전자 각각에게 다음 행동 한 문장
  - 완료 확인: 운전자 수락 + 통과 감지 + 요청자 탑승 확인이 모두 있어야 완료
- **놀라운 장면**: 수락 버튼을 눌러도 '탑승 완료'가 되지 않는다. 수락 뒤 정차면에 차가 들어오면 공간 확보가 다시 미완료로 뜬다.
- **선택 확장**: 두 번째 피코를 장난감 버스(운전자 패널)로 쓴다.

### ④ 막힘 위치를 재실험으로 좁히는 배수 점검대 (`drain_lab`) 23점 (2/3/4/5/5/4)
- **이야기**: 관리인이 물이 안 빠지는 빗물받이를 보고 무조건 '청소 완료'를 누르는 대신, 어디를 먼저 볼지 정하고 조치 뒤 다시 실험한다.
- **근거(약함, 그대로 밝힘)**: 다년 민원 키워드 없음. 빗물받이 70,579개(시설 수), 2022 침수 이력, FloodNet(초음파 센서망) 선행 사례
- **하드웨어**: 2칸 수조, 수위 센서 2개, 빗물 센서, 실험 시작·조치 버튼, SG90 점검 위치 포인터. 키트 외 약 1.2~2.4만원[추정]
- **AI**
  - jev: `normal / inspect_inlet / inspect_downstream / repeat_measurement / review`
  - chat 제안: 다음 점검과 예상 변화
  - 완료 확인: 같은 양으로 다시 실험해 기준 곡선에 가까워져야 개선으로 기록
- **놀라운 장면**: 유입부를 치워도 하류 때문에 개선되지 않는 경우를 보여 준다. 시스템은 완료를 선언하지 않고 다음 점검을 제안한다.
- **선택 확장**: 반지하 모형 차수판(서보). 실제 침수 방어를 보장하지 않는다.

### ⑤ 주민 요청을 반영하는 소음 조치 재측정 실험대 (`noise_lab`) 21점 (3/3/4/3/4/4)
- **이야기**: 작업자는 민원을 받고도 무엇을 바꾸면 나아지는지 모른다.
- **근거**: '소음 진동'(2019), '공사 소음' 12,063(2020), 2023 팔달구 소음 1,099건 중 공사 542건. SONYC 선행 사례
- **하드웨어**: 아날로그 마이크 2개(작업부·배경), 진동 센서, 주민 버튼, 조치 버튼, SG90 작업 전환 표지. 키트 외 약 1.4~2.6만원[추정]
- **AI**
  - jev: `observe / try_quiet_task / check_local_damping / background_or_uncertain / review`
  - chat 제안: 다음 실험(펠트 받침 / 조용한 작업 전환)
  - 완료 확인: 같은 길이의 전후 측정 창으로 '개선 관측 / 미확인 / 비교 불가'를 판정
- **놀라운 장면**: 펠트를 놓고 다시 두드려 비교한다. 멀리서 박수를 쳐 배경이 함께 커지면 성공으로 포장하지 않고 '비교 불가'를 띄운다.
- **리스크**: 강당 소음 간섭이 가장 크다. 그래서 시연·구현 점수를 3으로 낮췄다.

## 5. 스타터 코드 v2(`starter/`)
| 기능 | 내용 |
|---|---|
| jev 판단 | 프로필 6개: 기본 예제 `access_space` + 아이디어 5개. 확률 0.80 미만이면 review. 선택지 이름(`action`)은 피코 `actuate()`까지 전달하지만 경로별 화살표·분기 날개 동작은 아직 구현하지 않았다 |
| LLM 에이전트 제안 | `AGENT=1`. 조치가 바뀌면 chat이 `{speech, target 하나, level, reason, map_note}`를 '승인 대기'로 만든다. 노드 1개에서도 동작한다. 8초 간격 안의 변화는 최신 1건만 미뤄 처리하고, 호출 상한은 300회 |
| 사람 승인 | 대시보드 '승인' 버튼만. 60초 경과, 제안 뒤 관련 노드의 상황 키·조치 변화, 15초 넘은 보고 끊김 중 하나라도 있으면 폐기한다. 검사와 명령 등록은 한 잠금 안에서 한다 |
| 명령 전달 | 승인된 명령은 15초 동안 poll(1초, API 비용 없음) 응답마다 `cmd_id`와 함께 실린다. 피코는 같은 id를 다시 적용하지 않고, 단계를 올리기만 한다 |
| 음성 | `TTS=1`이면 승인된 문장만 한 번에 하나씩 읽는다(macOS 한국어 Yuna, Windows System.Speech) |
| 대시보드 | 노드 지도(SVG), 제안·승인 상태, jev 확률, 수동 요청서 초안 |
| 통신 | USB 기본(비차단 수신, 깨진 프레임 무시), Wi-Fi 선택. 오프라인이면 로컬 규칙 + 파랑 |

### 검증한 것(가짜 upstream = 문서 응답 형식을 흉내 낸 로컬 서버)
이 검증은 기존 기본 예제와 공통 중계 기능에 대한 것이다. §0-1의 통합 이동 상태·실물 시연을 검증한 결과가 아니다.
- 문법: 피코 코드는 `mpy-cross`, 서버는 `py_compile` 통과
- 회귀(USB·Wi-Fi·혼란 브리지): v1과 같은 단계 전이. 깨진 프레임 무시, 무응답 시 오프라인 후 복구
- 새 프로필 5개 `/decide` 왕복 정상. 서버가 시작할 때 선택지·단계 검사를 통과함
- 에이전트
  - 단일 노드에서 제안이 생성됨
  - 8초 안 변화가 미뤄졌다가 처리됨
  - 승인 전 poll에는 명령이 없음
  - 토큰 없는 승인은 401
  - 승인 뒤 같은 `cmd_id`가 반복 전달되어도 피코는 10초만 단계 2를 유지함(연장 없음)
  - 제안 뒤 대상 노드의 상황 키가 바뀌면 폐기됨
  - 관련 노드 보고가 15초 넘게 끊기면 폐기됨
- 음성: macOS에 한국어 음성 9개가 있고 Yuna가 있음을 확인했다. 파일로만 합성해 보고 스피커로 재생하지는 않았다. Windows 경로는 미검증

### 실제 API 확인(2026-10-31, 새 키)
- **jev 10건**(`access_space` 4, `route_guide` 4, `boarding_handoff` 2):
  - 가장 높은 확률을 받은 선택지는 10건 모두 예상과 같았다.
  - 확률은 0.47~0.97이었고 5건이 0.80 미만이라 `review`로 내려갔다.
  - 서버 측 지연은 0.59~2.2초였다(서버를 다시 띄운 직후 첫 판단은 3.2초).
  - 단차가 있는 A에도 0.26을 줬다. 단차 같은 필수 조건은 규칙으로 강제한다.
  - 0.80 기준은 시연 전 프로필별로 다시 정한다.
- **chat 버그를 찾아 고쳤다**:
  - 원인: `deepseek-v4.1-flash`는 추론 모델이라, 기존 `max_tokens` 300(에이전트)·600(요청서)을 추론에 다 써서 본문이 비었다(`finish_reason=length`). 에이전트 제안이 실호출에서 2번 모두 "에이전트 실패"였다.
  - 수정: `chat_text()`가 `reasoning_effort`(`CMD_TEXT_REASONING`, 기본 `low`)와 `max_tokens` 2,000을 보낸다.
  - 실측: `low`는 4.7~6.5초, 3번 중 3번 상태를 맞게 읽었다. `off`는 2.1~3.0초지만 6번 중 1번 상태를 잘못 읽었다(“A·B 모두 비어 있다”). 그래서 `low`를 기본으로 했다.
- **수정 후 종단 확인**:
  - jev 판단 → 제안 생성(7.2초, '승인 대기') → 대시보드 승인(HTTP 200) → 요청서 초안(5.0초, 201자, "원인과 책임은 단정하지 않습니다" 포함)
  - 이번 제안은 대상 노드가 없는 안내 문장이었다. 실제 `cmd`가 붙은 제안이 피코까지 가는 경로는 가짜 upstream으로만 확인했다.
- **ZDR**: `deepseek-v4.1-flash`에 `x-cmd-zdr: 1`을 붙인 요청이 HTTP 200으로 응답했다.

### 못 한 것
- `cmd`가 붙은 실제 제안 승인 → 피코 적용, TTS 스피커 재생, Windows 경로
- 실물 피코·센서·서보·핫스팟: 하드웨어가 없어 미검증
- 아이디어 1~5의 전용 피코 센서 처리·물리 동작·완료 검증과 §0-1의 이동 상태 전이·노드 간 인계는 미구현이다. 현재 피코 코드는 `access_space` 기본 예제이며, 중계 서버의 5개 프로필이 있다고 완성된 하드웨어 동작을 뜻하지는 않는다.

## 6. 토론 요약(4·5라운드)
- **독립 조사**: 수상작이 거의 겹치지 않았다(공통은 Argus 하나). 그런데도 다섯 문제 영역과 순위가 같은 방향으로 나왔다. 양쪽 모두 1순위가 접근성 경로 안내다.
- **GPT에서 가져온 것**: 센서로 완료를 검증해 허위 완료를 막는 설계, 허용 목록 안의 단일 행동 + 사람 승인, 배수 재실험·소음 전후 비교라는 실험형 설계, 시각장애인 안전장치로 과장하지 않기
- **Claude에서 가져온 것**: 저녁·밤 시민 신고 의존 데이터(794,738건 분석), 선택 확장 노드(두 번째 피코), 도구 호출 없이 프롬프트에 맥락을 바로 넣기(GPT 동의), 승인된 문장만 읽는 음성 안내
- **GPT가 에이전트 구현에서 찾은 결함 5개 → 모두 수정·재검증**
  1. 피코 버튼이 전역 최신 제안을 승인함 → 대시보드 ID 승인만 남기고 자동 적용 모드 삭제
  2. 조치 이름만 비교해 낡은 상황에서도 승인됨 → 상황 키 rev와 보고 시각 검사
  3. 복수 명령 허용, 높은 명령을 낮은 명령이 덮음 → 단일 대상, 서버·피코 모두 최댓값 유지
  4. 응답 전에 명령이 삭제됨 → 만료까지 `cmd_id`와 함께 반복 전달하고 피코가 중복 적용을 막음
  5. 노드 1개면 제안이 안 생기고, 간격 중 변화가 버려짐 → 단일 노드 허용, 최신 1건 미뤄 처리
- 원문: `debate/claude_round4_upgrade.md`, `astra/round4.md`, `astra/round5.md`

### 6-1. 초보팀 전제 철회 후 판정(6라운드)

- 민원 신고 비중의 장애물 발생 확률 해석과 서보로 사람을 미는 설계는 제외했다. 새 점수나 실물 성능을 합의한 것은 아니다.

### 6-2. LLM 역할 판정(7라운드)
- 사용자 질문 "llm은?"에 대해 Claude는 통합안에서 LLM 비중이 약하고 "규칙으로 되지 않느냐"는 질문에 취약하다고 진단했다. 그래서 LLM을 언어 계층으로 두자고 제안했다.
- GPT 판정은 **수정 채택**이다.
  - 1순위는 요구·제보 구조화, 2순위는 기존 `/report` 유지로 정했다. 대상별 안내는 템플릿으로 처리한다.
  - '불법' 민원 유형 판정은 기각했다(위반 판단과 같은 효과).
  - 위험 두 가지를 더했다: 오독·지시 주입, 외부 전송 개인정보.
  - 평가는 템플릿 기준선과 비교하고 문장 세트는 프롬프트와 분리한다.
- Claude는 전부 수용하고, 개인정보 위험에는 Command Code 문서의 ZDR 근거(jev 미지원, chat은 헤더로 강제)를 더했다. 새 점수나 실호출 검증은 아니다.
- 원문: `astra/round7_llm.md`
