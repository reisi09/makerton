# 4라운드: 수상작의 설계를 12시간 제작 범위로 줄인 고도화안

## 1. 결론과 순위

**1번 ‘접근성 경로 안내’를 우선 권한다.** 기존의 ‘막혔다’는 알림을 ‘이용 가능한 길 선택 → 실제 안내 → 도착·복구 확인’으로 바꾼다. 2번은 종이공의 배출 경로가 바뀌는 장면으로 물리적 작동을 가장 분명하게 보여 줄 수 있다.
수상작에서 가져올 것은 비싼 센서나 거대한 서비스가 아니라 **측정한 사실이 다음 행동을 바꾸고, 그 행동의 결과를 다시 확인하는 구조**다. 다중 에이전트·실시간 도시 지도·자체 모델 학습은 이번 MVP에서 제외한다.
아래 점수는 구현·수상을 보장하는 실측값이 아니라 설계 비교다[추정][INFERENCE]. 5점은 이 행사 제약에서 강함, 3점은 조건부, 1점은 부적합이다. ‘참신성’은 기존 5개 대비 차별성과 심사 설득력이며 세계 최초라는 뜻이 아니다.

|---|---|---:|---:|---:|---:|---:|---:|---:|

| 3 | 요청부터 탑승까지 이어지는 승차 인계 보드 | 4 | 4 | 4 | 4 | 5 | 4 | **25** |

1·3번은 접근·교통 관련 직접 키워드가 강하지만, 민원이 해당 장치를 원한다는 증거까지는 아니다. 2번은 청소 부서 통계가 간접 근거여서 3점이다. 4번은 직접 민원 추이가 없고 수조 제작이 필요하다. 5번은 강당 소음 간섭과 조치 효과의 재현성이 약하다. 그래서 기능이 늘었다는 이유로 구현·근거 점수를 올리지 않았다.

## 3. 반복되는 설계 패턴 7개

1. **사용자를 한 사람으로 좁힌다.** REWEBA·Argus·Storm Shield는 ‘시민 전체’보다 구체적인 이용자의 제약이 먼저다. 우리도 ‘접근 경로가 막힌 휠체어 이용자’, ‘두 배출장소를 맡은 관리인’으로 시작한다.
2. **출력은 다음 행동을 바꾼다.** FarmX의 작물 추천, SmartScale의 할인, REWEBA의 의료진 연결처럼 선택·담당자·후속 행동을 정한다. 빨간불만 켜고 끝내지 않는다.
3. **순간값보다 맥락과 변화를 쓴다.** Peel의 기준 측정·용출 곡선, AKQUA-Gel의 지속 관찰처럼 정상 기준과 시간 경과를 함께 본다. 우리는 점유 지속시간·수위 하강·조치 전후 창을 보낸다.
4. **물리 측정과 언어 추론을 분리한다.** Peel·HawkWatch처럼 측정·전처리와 설명·근거 조회의 역할이 다르다. Pico는 센서 요약, jev는 상황 판단, chat은 허용된 다음 행동의 계획·설명을 맡는다.
5. **현장 정보가 필요한 사람에게 전달되게 한다.** REWEBA·AKQUA-Gel의 전문가 연결과 H.E.A.T.M.A.P.의 장소별 정보에서 가져온다. 여러 보드를 설치하는 대신, MVP에서는 요청자·작업자 사이의 접수·수락·완료를 보이게 한다.
6. **불확실성을 제품의 상태로 만든다.** Peel의 ‘확인 불가’, ECGo의 잡음 문제, SmartScale의 작은 실험 범위를 숨기지 않는다. 우리도 센서 오류·판단 보류·조치 무효를 정상 경로와 나란히 시연한다.
7. **새 부품보다 사용 방식의 결합을 바꾼다.** Iris의 스마트폰 재사용, Argus의 안경 부착, Storm Shield의 보청기 보완에서 가져온다. 이번에는 기본 센서에 경로 선택·작업 인계·재측정을 결합한다.

## 4. 현재 5개가 단순해 보이는 이유

| 기존 안 | 진단: 아이디어별 2문장 이내 |
|---|---|
| 보행로·접근공간 점유 안내 | 막힌 곳은 알려 주지만 이용자가 어디로 가야 하는지는 남는다. 자리가 비었다는 확인과 실제 이동 완료도 구분하지 않는다. |
| 공동 배출장소 넘침·방치 알림 | 넘침을 감지한 뒤 배출을 어디로 돌릴지, 무엇부터 수거할지 없다. 완료 버튼만으로는 거짓 완료를 막지 못한다. |
| 버스정류소 진입공간·승차 도움 | 요청 표시가 켜져도 운전자가 보았는지, 도움을 수락했는지, 실제 탑승했는지 알기 어렵다. 도움 요청이 사람 사이에서 사라지는 문제가 남는다. |
| 빗물받이 배수 지연 경보 | 높은 수위는 보이지만 어떤 점검을 먼저 하고 개선 여부를 어떻게 확인할지 없다. 민원 근거가 약한 문제를 센서 추가만으로 보완할 수도 없다. |
| 공사장 지속 소음 작업 알림 | 시끄럽다는 사실을 반복할 뿐 작업자가 무엇을 바꿔야 하는지 없다. 조치 후 정말 달라졌는지 보여 주지 못하면 일반 소음 경보기와 차이가 작다. |

## 5. 다섯 안에 공통으로 적용할 구현 계약

- **범위:** 팀당 아래 한 안만 제작한다. 각 MVP는 **Pico WH 1대, 노트북 1대**다. 여러 센서 지점·모형 구역은 한 보드에 유선 연결하며 ‘여러 무선 노드’라고 부르지 않는다. 노트북 화면은 고정 배치도·작업 카드·센서 변화 그래프만 구현한다.
- **통신:** 기존 스타터를 바탕으로 USB 직렬 → 노트북 중계 → Command Code HTTPS를 쓴다. 키는 노트북 환경변수에만 둔다. 노트북은 휴대폰 인터넷을 이용하고, Pico Wi-Fi는 확장으로 뺀다. 단말 간 핫스팟 차단·Pico TLS·키 저장 문제를 제작 범위에서 제거한다.
- **AI 판단:** `https://api.commandcode.ai/provider/v1/systemone`, 모델 `typesafe/jev`. 텍스트 `state`에 `seq`, 안정 상태가 바뀔 때만 증가하는 `rev`, 센서 요약·지속시간·요청·직전 조치를 넣는다. `questions.next`는 `type:"choice"`, `instructions`는 아래 각 안의 질문, `criteria`는 선택지 ID→의미의 객체다. 원시 음성·개인정보는 보내지 않는다.
- **AI 계획·설명:** 사용자가 ‘다음 행동 제안’을 누르면 `/chat/completions`, 모델 `deepseek/deepseek-v4.1-flash`를 호출한다. 허용 도구는 노트북의 읽기 전용 `read_context(seq, rev)` 하나이며 각 안의 경로·작업·기준 실험을 반환한다. 도구 호출은 최대 1회, 그 결과를 받는 최종 응답까지 최대 2요청이다. 웹 검색·셸 실행·자동 신고·임의 장치 제어는 없다.
- **출력 계약:** chat은 `{seq, rev, action_id, target_id, reason, expected_change}`를 반환한다. `action_id/target_id`는 각 안의 허용 목록 안에서만 고르고, 사람이 확인한 뒤 안내 장치를 움직인다. 수락·탑승·수거 완료 같은 사실을 LLM이 생성하거나 도구로 기록할 수는 없다.
- **실행 제한:** jev의 선택된 항목 확률 `answers.next.probabilities[choice]`가 `0.80` 미만이면 `review`다. `0.80`은 검증 전 초기값이며 실제 안전 확률이 아니다. JSON 오류·잘못된 선택지·다른 요청의 `seq`·달라진 `rev`는 적용하지 않는다. 승인 순간 센서 수신도 최근 2초 이내여야 한다. 매 샘플마다 `rev`를 바꾸면 정상 API 응답도 모두 낡아지므로 점유·요청 등 의사결정 상태가 바뀔 때만 증가시킨다.
- **지연·단절:** 각 API 요청 제한은 6초, chat 도구 왕복 전체는 12초다. 기다리는 동안 Pico의 측정·버튼·화면은 계속 동작한다. 단절·오류 시 신규 AI 제안과 방향 안내를 중지하고 중립 위치·‘확인 필요’를 표시한다. 센서 오류를 정상·빈 공간으로 처리하지 않는다. 긴급 수위 알림 등 로컬 규칙은 안전·오프라인 대비이며 AI 판단을 했다고 표시하지 않는다.
- **측정·전원:** HC-SR04는 순차 발사해 간섭을 줄이고 ECHO를 저항 분압해 3.3V로 낮춘다. SG90은 별도 5V 전원과 공통 GND를 사용한다. 물은 트레이 안, 회로는 밖에 둔다. 실제 차단기·차량·펌프·전원 릴레이를 제어하지 않는다.
- **호출·비용 예산[추정]:** 3시간 시연에서 상태 변화 때만 jev를 요청하며 최대 480회, 회당 입력 800토큰으로 잡는다. chat은 수동 계획 20회 × 최대 2요청, 요청당 입력 1,500·출력 350토큰 가정이다. jev `$0.016128` + chat 비혼잡 시간 `$0.017400` = **약 `$0.034/팀`**. chat 혼잡 요금이면 합계 약 `$0.051`이다. 토큰 가정과 호출 상한에 따른 계산이지 실제 청구 결과가 아니다. [공식 API 문서][provider]·[모델 요금][pricing] 기준이며, 현재 문서상 혼잡 시간은 평일 KST 10:00~13:00·15:00~19:00이므로 11/1 일요일 시연에는 비혼잡 요금을 적용했다.
- **사전 조건:** 기존 `최종_산출물.md`에는 `401 "Your API key has expired"`가 기록되어 있다. 유효 키와 사용자 호출 승인이 필요하다. 이번 조사에서는 API를 호출하지 않았고, 새 설계의 실제 모델 응답·하드웨어 동작도 확인하지 않았다. 실패 시 녹화·고정 출력을 실제 AI 응답으로 위장하지 않는다.
- **부품 견적 기준[추정][INFERENCE]:** 키트에 Pico WH·USB·브레드보드·점퍼·저항·LED·버튼·SG90 1개가 있다고 가정한다. 아래 센서는 보수적으로 전부 추가 구매하는 금액이며 키트에 있으면 뺀다. 노트북·휴대폰은 기보유, 배송비 제외. 국내 소매 예산 범위이지 판매처 확정 견적은 아니다. SG90이 키트에 없으면 별도로 3,000~5,000원을 더한다.

## 6. 고도화 아이디어 5개

### 1) 막힌 길을 다시 잇는 접근성 경로 안내

- **사용자 이야기:** 휠체어 이용자가 목적지로 가는 짧은 길 앞에서 적치물을 만난다. ‘막혔다’가 아니라 사전에 확인된 다른 통로 또는 도움 요청을 안내받고, 관리인은 어느 구간을 복구해야 하는지 안다.
- **민원·SDG:** ‘인도 불법’ 문서빈도는 **2023년 20,615 → 2024년 34,982 → 2025년 31,182**다([E2][e2]). 고유 위반 건수·휠체어 불편 건수는 아니다. [SDG 11.2·11.7][sdg11]: 교통약자의 접근성과 공공공간 접근.
- **참고·패턴:** W3 Iris·W6 Argus의 이용자 부담 감소, W1 Peel의 근거 조회·판단 보류. 카메라 인식을 복제하지 않고 ‘현재 관측 + 사전 확인된 통로 정보’를 결합한다.
- **시스템:** Pico 1노드; HC-SR04 2개로 두 통로의 좁은 구간을 관측, 요청·도착 버튼, 두 경로 LED와 SG90 방향 화살표. USB로 고정된 A/B 배치도·통로별 점유 지속시간을 노트북에 표시한다.
- **jev 질문:** “일시 통과와 지속 점유, 요청자의 이동 조건을 볼 때 어느 안내를 검토할 것인가?” 선택지는 `route_a/route_b/ask_helper/review`. 양쪽 통로의 상태·센서 오류·지속시간·사전 등록한 경사/폭 정보를 입력한다. 센서 두 개로 전체 경로의 안전을 보장하지 않는다.
- **chat 역할:** `read_context`로 A/B 통로의 접근 조건과 최신 판단을 조회하고, `guide_a/guide_b/request_help/wait` 중 하나와 이유를 제안한다. 사전 점검에서 부적합한 경로는 후보에서 제거하므로 LLM이 계단 경로를 추천할 수 없다. 승인 후 화살표가 실제 방향을 가리킨다.
- **12시간 MVP:** 목적지 1개·모형 통로 2개·이용 조건 2종·현재 요청 1개. 도착 버튼은 이동 완료, 센서의 장애물 제거 확인은 통로 복구로 따로 기록한다. **확장 제외:** 실제 도시 길찾기·GPS·모바일 앱·다수 Pico·통행 가능 인증.
- **놀라운 시연:** 심사위원이 A에 장애물을 놓으면 B 안내를 제안한다. B도 막으면 그럴듯한 길을 만들어 내지 않고 도움 요청으로 전환한다. A를 치우면 복구를 관측하고 새 승인을 거쳐 방향이 바뀐다. 모두 예상 시나리오이며 실제 모델의 선택은 제작 중 확인해야 한다.
- **심사 포인트·확인 지표:** 같은 ‘점유’라도 사용자의 이동 조건에 따라 다음 행동이 달라진다. 두 길 개방/A 폐쇄/B 폐쇄/둘 다 폐쇄/센서 오류에서 금지 경로 안내가 없는지, 실제 버튼 없이 도착을 기록하지 않는지 확인한다. 민원 감소율을 만들어 내지 않는다.
- **리스크·대응:** 초음파가 통로 전체를 보지 못한다. 관측 지점을 좁은 목으로 한정하고 미관측 구간은 ‘사전 점검 정보’로 구분한다. 실제 길에서는 현장 재점검이 필요하며 시각장애인 단독 보행용 안전장치로 제시하지 않는다.
- **키트 외:** HC-SR04 2개 4,000~8,000원 + 모형 3,000~5,000원 + 5V 서보 전원 구성 5,000~8,000원 = **12,000~21,000원[추정]**. 촉각 알림은 진동 모터·구동 소자 3,000~6,000원 선택 추가이며 MVP 필수는 아니다.

### 2) 배출 분산과 수거 완료를 검증하는 공동 수거 스테이션

- **사용자 이야기:** 두 배출장소를 맡은 관리인이 한쪽의 넘침과 통로 적치물을 동시에 만난다. 주민에게는 이용 가능한 쪽을, 관리인에게는 먼저 처리할 일을 제시하고 실제 처리 여부까지 확인한다.
- **민원·SDG:** ‘쓰레기 투기’는 **2025년 df 2,520**([E2][e2]); 청소 담당 부서 접수는 **2020년 4,185건·2023년 3,379건**([E3][e3]). 후자는 넘침 신고량이 아니라 행정 수요의 간접 근거다. [SDG 11.6][sdg11]의 도시 폐기물 관리에 연결하며 재활용률 증가까지 주장하지 않는다.
- **참고·패턴:** W8 SmartScale의 ‘판단 → 이용자의 선택 변경’, W7 FarmX의 상태 기반 권고, W11 H.E.A.T.M.A.P.의 장소별 비교. 단순 쓰레기통 표시가 아니라 배출·수거 순서를 함께 바꾼다.
- **시스템:** Pico 1노드; HC-SR04 3개로 A/B 적재 높이와 공용 접근부 적치 관측. RGB·완료 버튼·SG90으로 가벼운 종이공용 분기 날개를 움직여 A/B 모형 통으로 유도한다. 노트북은 두 장소·미완료 작업을 표시한다. 실제 생활폐기물을 자동 분류하는 장치는 아니다.
- **jev 질문:** “적재·방치 지속시간과 접근부 상태를 볼 때 지금 배출을 안내해도 되는 곳은?” `use_a/use_b/hold/review`. 통로 방치와 수거 필요성은 같은 요청의 추가 `noul` 질문으로 묻는다. 가득 참·장애물·반사 오류를 구분한다.
- **chat 역할:** `read_context`에서 두 장소의 상태, 미완료 작업, 관리인의 가용 시간을 받아 `clear_access/empty_a/empty_b/wait` 중 첫 작업과 다음 작업을 설명한다. 행동 ID는 한 번에 하나만 승인한다. AI 안내와 실제 빈 공간 검사가 모두 통과한 쪽으로만 분기 날개가 움직인다.
- **12시간 MVP:** 통 2개·접근부 1곳, 종이공만 사용. ‘수거 완료’는 버튼 확인과 교정한 비움 기준 이하의 연속 측정이 모두 있어야 인정하고, 통로 정리는 별도 상태로 남긴다. **확장 제외:** 재질 인식·수거차 최적 경로·자동 압축·실제 투입구 잠금.
- **놀라운 시연:** A를 채우면 종이공이 B로 간다. 접근부에 상자를 놓으면 배출을 보류하고 통로 정리 작업을 제안한다. 아무것도 치우지 않고 완료를 눌러도 작업은 사라지지 않으며, 실제 비운 뒤에만 닫힌다.
- **심사 포인트·확인 지표:** 경고 이후 주민과 관리인의 행동이 모두 달라지고, 허위 완료를 센서가 막는다. A/B 전환, 양쪽 만재 보류, 통로 방치, 완료 버튼만 누름, 실제 수거를 각각 확인한다.
- **리스크·대응:** 불규칙한 쓰레기 표면은 높이 측정을 흔든다. 종이공·평평한 시험판으로 기준을 잡고 연속 측정의 중앙값을 사용한다. 초음파는 순차 측정, 분기 날개는 손이 닿아도 위험하지 않은 가벼운 모형만 쓴다.
- **키트 외:** HC-SR04 3개 6,000~12,000원 + 통·종이 분기판 3,000~5,000원 + 서보 전원 5,000~8,000원 = **14,000~25,000원[추정]**.

### 3) 요청부터 탑승까지 이어지는 승차 인계 보드

- **사용자 이야기:** 교통약자가 정류장에서 도움을 요청했지만 운전자가 확인했는지 모른다. 요청자는 수락 여부를 확인하고, 운전자는 공간 확보·도움·탑승 중 무엇이 아직 남았는지 구분한다.
- **민원·SDG:** ‘버스정류소 불법’은 **2023년 df 5,604·2024년 6,019·2025년 4,518**([E2][e2]). 이는 정류소 접근 문제의 근거이며 ‘도움 요청 누락’의 발생 건수를 증명하지는 않는다. [SDG 11.2][sdg11]: 교통약자를 고려한 대중교통 접근성.
- **참고·패턴:** W5 REWEBA의 전문가 인계, W9 Storm Shield의 보조기기 보완, W6 Argus의 낮은 조작 부담. 감지보다 요청이 사람 사이에서 끊기지 않는 과정에 초점을 둔다.
- **시스템:** Pico 1노드에 유선 요청자·운전자 패널 2개. HC-SR04 1개로 모형 진입공간 관측, 요청·수락·도착 모사·탑승확인 버튼, 적외선 센서 1개로 모형 통과 관측, RGB·SG90 도움 표지·진동 알림. 노트북은 요청→수락→탑승 상태를 표시한다.
- **jev 질문:** “요청 내용·진입공간 점유·도착·수락 상황에서 어떤 안내가 우선인가?” `clear_space/offer_help/both/review`. 휠체어·유모차 등은 사용자가 선택한 지원 조건이며 센서가 장애·자격을 추론하지 않는다.
- **chat 역할:** `read_context`로 미완료 단계·지원 조건·공간 상태를 조회해 요청자와 운전자에게 각각 다음 행동 한 문장을 제안한다. `show_space_request/show_help_request/show_wait`만 승인 가능하다. 운전자의 수락은 실제 버튼으로만 발생하며 LLM 답변이 수락을 대신하지 않는다.
- **12시간 MVP:** 요청 1건, 정류소 1곳, 버스 도착은 버튼으로 명시적 모사. 수락 시 진동하며, 운전자 수락·통과 관측·요청자의 탑승확인이 모두 있어야 완료한다. **확장 제외:** 버스 도착 API·실제 운전자 단말·전동 발판·개인식별·다중 요청 배차.
- **놀라운 시연:** 운전자 수락 버튼을 눌러도 ‘탑승 완료’가 되지 않는다. 수락 뒤 새 장애물이 생기면 공간 확보가 미완료로 남고, 모형 통과와 탑승확인 뒤에만 요청이 닫힌다. 진동으로 수락 사실도 직접 체험한다.
- **심사 포인트·확인 지표:** 요청 표시등과 달리 ‘접수했지만 해결하지 못한 상태’를 드러낸다. 미수락·수락만 함·통과만 함·확인까지 함을 구분하고, 임의의 센서 통과만으로 탑승을 판정하지 않는다.
- **리스크·대응:** 적외선은 사람 신원이나 실제 승차를 알 수 없다. 모형 통과와 버튼의 결합을 시연 범위로 한정하고 실제 운송 시스템 연동으로 과장하지 않는다. 진동 모터는 GPIO 직결 대신 구동 소자를 쓴다.
- **키트 외:** HC-SR04 2,000~4,000원 + 적외선 센서 1,000~3,000원 + 진동 모터·구동 소자 3,000~6,000원 + 패널 3,000~5,000원 + 서보 전원 5,000~8,000원 = **14,000~26,000원[추정]**.

### 4) 막힘 위치를 재실험으로 좁히는 배수 점검대

- **사용자 이야기:** 관리인이 물이 빠지지 않는 배수구를 발견한다. 무조건 청소 완료를 누르는 대신 유입부·하류 수위를 비교해 먼저 확인할 곳을 정하고, 같은 조건으로 다시 부어 개선 여부를 확인한다.
- **민원·SDG:** **2019~2025년 상위 100 키워드에 빗물·침수·배수·하수가 없다**([E2][e2]); 문제 부재가 아니라 직접 다년 근거의 부재다. **2026년 5월 빗물받이 70,579개**는 시설 수이고 민원 수가 아니다([E6 기사][drain]). [SDG 11.5][sdg11]의 수재해 피해 저감에 연결하지만 피해 감소량은 측정하지 않는다.
- **참고·패턴:** W1 Peel의 기준 측정·판정 불가, W12 Ice Savers의 위험 장소 원격 관측, W11 H.E.A.T.M.A.P.의 위치별 비교. ‘높은 물’보다 ‘어떤 점검 뒤 어떻게 달라졌는가’를 보여 준다.
- **시스템:** Pico 1노드; 연결된 투명 용기 2개에 상대 수위 센서 2개, 빗물 센서 1개, 실험 시작·조치 버튼, LED·SG90 점검 위치 포인터. USB 대시보드는 상류/하류 수위와 정상 배수 곡선을 겹쳐 표시한다. 물은 사람이 정량 컵으로 붓는다.
- **jev 질문:** “동일 투입량의 기준 실험과 현재 상·하류 수위 변화를 비교하면 다음 점검은?” `inspect_inlet/inspect_downstream/repeat_measurement/review`. 원인 확정·도시 침수 예측이 아니라 다음 관찰을 고르는 질문이다.
- **chat 역할:** `read_context`에서 기준 곡선·현재 곡선·수행한 조치를 받아 ‘모형 필터 확인’ 또는 ‘하류 용기 상태 확인’ 중 하나를 제안하고 예상 관측 변화를 설명한다. 포인터가 점검할 위치를 가리킨다. 새로운 실험 전에는 이전 조치가 효과 있었다고 요약할 수 없다.
- **12시간 MVP:** 정상·유입부 막힘·하류 수위 높음의 세 실험, 조치 뒤 같은 양의 물 재투입, 센서가 지지할 때만 회복 기록. **확장 제외:** 강우 예보·실제 하수관 원인 진단·펌프·자동 수문·도시 범람 지도.
- **놀라운 시연:** 유입부를 치워도 하류 수위 때문에 배수가 개선되지 않는 경우를 보여 준다. 시스템은 청소 완료를 선언하지 않고 다음 점검을 제안한다. 하류를 정리하고 재측정했을 때 두 곡선이 기준에 가까워지는 장면으로 끝낸다.
- **심사 포인트·확인 지표:** 조치 실패도 발견하는 작은 현장 실험 도구다. 같은 투입량에서 정상 기준·배수 소요시간·조치 전후 수위 하강을 비교하되, 한 번의 시연으로 막힘 위치 진단 정확도를 주장하지 않는다.
- **리스크·대응:** 저가 전극 수위 센서의 부식·전도도·위치 편차가 크다. 짧은 시연에만 쓰고 눈금·동일한 물·고정 위치로 보조 확인한다. 센서 범위를 벗어나면 재측정, 물과 보드는 분리한다. 근거가 약하므로 최우선 추천은 아니다.
- **키트 외:** 수위 센서 2개 2,000~6,000원 + 빗물 센서 1,000~2,000원 + 용기·관·트레이 4,000~8,000원 + 서보 전원 5,000~8,000원 = **12,000~24,000원[추정]**.

### 5) 소음 조치의 효과를 다시 재는 작업 전환 실험대

- **사용자 이야기:** 작업자가 민원을 받고도 무엇을 바꾸면 나아지는지 모른다. 지속 작업 소리와 주변 소음을 함께 관측하고, 사전 등록한 저소음 대안 중 하나를 시도한 뒤 효과를 확인한다.
- **민원·SDG:** **2023년 팔달구 소음 민원 1,099건 중 공사 소음 542건**([E6 기사][noise]); 수원 전체 수치가 아니다. **2020년 ‘공사 소음’ df 12,063**도 확인된다([E2][e2]). 공사 중단 키워드를 소음으로 합산하지 않는다. [SDG 3.4][sdg3]의 정신건강·안녕과 간접 연결되며 건강 개선을 측정한 것은 아니다.
- **참고·패턴:** W1 Peel의 기준·품질 검사, W4 ECGo의 잡음 한계, W8 SmartScale의 행동 선택. ‘시끄럽다’는 경고를 반복하지 않고 조치 전후의 근거를 남긴다.
- **시스템:** Pico 1노드; 작업부·배경의 아날로그 마이크 2개와 진동 센서 1개, 작업·조치 버튼, RGB·SG90 작업 전환 표지. Pico는 DC 바이어스를 뺀 짧은 구간 RMS·지속 비율·진동 여부만 요약하고 노트북은 두 위치의 기준 대비 변화를 표시한다. 녹음 저장·전송은 없다.
- **jev 질문:** “작업부·배경 변화와 진동의 동시성을 볼 때 작업 조치가 필요한가?” `try_quiet_task/check_local_damping/background_or_uncertain/review`. 값은 상대 지표이지 dBA·법적 위반 판정이 아니다. 두 마이크 수치를 단순 차감해 소음원을 분리했다고 주장하지 않는다.
- **chat 역할:** `read_context`로 전후 측정 창, 시도한 조치, 허용 대안인 ‘펠트 받침’·‘조용한 작업으로 전환’을 조회한다. `try_pad/switch_task/repeat_measurement` 중 다음 실험을 제안하고, 재측정 뒤 `개선 관측/개선 미확인/비교 불가`를 실제 수치에 근거해 설명한다.
- **12시간 MVP:** 반복 두드림 모형 1개, 두 대안, 동일 길이의 전후 측정 창. 선택된 행동은 표지로 보여 주고 사람이 수행한다. **확장 제외:** 실제 공구 정지·능동 소음 제거·절대 소음계·음성 인식·민원인 위치 추적.
- **놀라운 시연:** 펠트를 놓고 다시 두드려 결과를 비교한다. 심사위원이 멀리서 박수쳐 두 지점이 함께 커지면 성공으로 포장하지 않고 비교 불가를 표시한다. 효과 없는 조치에서는 완료가 아니라 다음 실험이 남는다.
- **심사 포인트·확인 지표:** AI의 자신감보다 ‘조치를 했는데 효과가 없었다’는 사실을 확인하는 능력을 강조한다. 동일 작업 반복·받침 변경·배경 소리 개입에서 결과를 구분한다. 실제 소음 저감률은 제작 후 관측하기 전에는 제시하지 않는다.
- **리스크·대응:** 강당 반사음·마이크 편차·손 두드림 차이로 효과가 재현되지 않을 수 있다. 두 센서를 각각 기준화하고 정해진 위치·횟수로 반복한다. 개선이 관측되지 않으면 그대로 보여 주며, 조용한 장소에서 얻은 결과를 강당 실측처럼 쓰지 않는다.
- **키트 외:** MAX4466급 아날로그 마이크 2개 6,000~12,000원 + 진동 센서 1,000~2,000원 + 펠트·모형 2,000~4,000원 + 서보 전원 5,000~8,000원 = **14,000~26,000원[추정]**. 마이크는 기본 키트 부품을 대체하는 저가 선택 부품이다.

## 7. 12시간을 지키는 제작·검증 범위

기존 스타터 재사용을 전제로 한 작업 배분[추정]이다. 새 기능이 이미 스타터에 구현되어 있다는 뜻은 아니다. 2인은 하드웨어/중계·화면을 나누고, 3인이면 시나리오·교정·모형을 분리한다. 유효 키와 호출 승인이 없으면 실제 AI 시연 가능 여부는 미확인으로 남는다.

| 경과 시간 | 완료 기준 |
|---|---|
| 0~1h | USB·환경·부품 확인, 승인된 경우에만 API 연결 확인. 핵심 센서 결품·키 문제를 먼저 드러낸다. |
| 1~3h | 모든 센서 값·오류 상태를 화면에서 확인하고 모형·서보를 별도로 동작시킨다. |
| 3~5h | 정상·이상·센서 오류를 각각 기록하고 센서 요약·기준 실험을 고정한다. |
| 5~7h | jev 질문, 읽기 전용 도구 1개, chat 최종 JSON·허용 행동 검사를 연결한다. |
| 7~9h | 사람의 승인 → 물리 안내 → 실제 조치 → 재측정·완료 기록을 연결한다. |
| 9~11h | 잘못된 완료, 상태가 바뀐 뒤의 응답, API 지연·단절, 센서 무반사·오류를 직접 넣어 확인한다. |
| 11~12h | 90초 시연을 반복한다. ‘문제 발생 → 선택이 바뀜 → 행동 → 결과 확인’과 실패 장면 하나를 모두 보여 준다. |

예측 정확도·민원 감소율·안전 인증 대신, **센서가 바뀌면 선택이 바뀌는가, 사람이 하지 않은 일을 완료했다고 기록하지 않는가, 실패를 드러내는가**를 시연의 판정 기준으로 삼는다. 성능·추가 비용·제작 시간은 모두 제작 전에 검증할 가정이며, 이 문서는 하드웨어 제작이나 API 실행 결과가 아니라 독립 조사에 따른 제안서다.
