# 12라운드: 최신 트렌드로 과제 재선정
**결론: 「분리배출 코치」를 교체한다. 1순위는 「Pico Forge — 말로 만들고 실물로 검증하는 AI 메이커」다.** SDG를 버리는 것이 아니라, 기술적 성취를 먼저 보여주는 선택이다.
출처 날짜는 원문 게시일이며 수정·갱신일은 별도 표시했다. 공식 발표·구현 사례·수상 사실과, 이를 이번 대회에 적용한 판단을 구분한다.

## 2. 분리배출 코치 판정: 유지·이름 변경보다 교체
- 강점은 여전히 있다. 품목의 모호한 설명을 되묻고 지침을 연결하는 LLM, 투입 감지·덮개를 맡는 MCU는 역할이 구분된다. SDG 주제라서 경쟁력이 없다는 근거는 없다.
- 다만 사용자 요구는 ‘환경교육 기기’보다 최신 기술이 먼저 보이는 과제다. 카메라 없이 센서로 재질을 판별할 수 없고, 안내 뒤 덮개를 여는 것만으로는 T6·T8의 실행·검증형 에이전트보다 기술적 차별성이 약하다.[추정]
- ‘순환경제 에이전트’로 이름만 바꾸는 재구성은 채택하지 않는다. 같은 문제에서 차별화하려고 로봇 분해·자동 선별을 추가하면 주어진 부품·12시간 범위를 벗어날 위험이 크다.[추정]

## 3. 후보 3개: 공통 구현 경계
- 공통 구조: **텍스트 입력 → 노트북의 Command Code chat 도구 호출 → USB 직렬 → Pico → 센서 결과 회신**. `deepseek-v4.1-flash`만 전제하며 jev·STT·카메라는 쓰지 않는다. Pico에서 LLM을 돌리지 않는다.
- MCP는 트렌드 근거이지 필수 구현물이 아니다. MVP는 기존 function calling과 제한된 장치 도구로 만든다. MCP를 구현하지 않았는데 ‘MCP 지원’이라고 발표하지 않는다.
- 새 동작 계획은 사람이 승인한다. 서보 범위·작동 시간 제한·정지·통신 단절 처리는 Pico 규칙이 담당한다. 임의 생성 코드 실행이나 상용 전원 장치 제어는 제외하고 종이·저전압 모형만 쓴다.
- 공통 전제[추정]: 조도·초음파·버튼·LED·서보가 키트에 있다. 정확한 구성은 미확인이고 미포함 부품 보충비는 5천~1.5만원[추정]. Pico만 가능한 것은 아니지만, 세 후보 모두 물리적 입출력과 독립 제어를 맡는 MCU가 필요하다.
- **아래 구현 가능성·효과·12시간 배분·90초 시연 시간은 모두 [추정]이다.** 사용자 제공 지연값인 호출 3.4~4.1초·루프 10~16초를 전제로 하고, 빠른 장치 반응은 LLM 응답을 기다리지 않는다.

### ① Pico Forge — 말로 만들고 실물로 검증하는 AI 메이커
- **트렌드 근거:** T6·T8의 자연어 하드웨어 개발·실물 피드백. 단순 코드 생성 대신 ‘요구 해석 → 동작표 → 승인 → 실물 시험 → 수정’에 집중한다. 대상은 센서 작품을 만드는 학생이다.
- **피코의 필요성:** 접근·밝기·버튼을 실제로 읽고 서보·LED를 구동한다. 노트북 시뮬레이션으로는 드러나지 않는 센서 반응을 시험하며, 네트워크와 무관하게 안전 한계를 지킨다.
- **LLM의 필요성:** “다가오면 열되 어두울 때는 안 돼” 같은 자유문장의 조건·예외를 풀고 모호한 기준을 되묻는다. 센서 기록과 요구가 어긋나면 수정안을 만든다. 숫자 임계값 판정과 실행은 규칙이다.
- **12시간 MVP:** 입출력·USB 3h / 최대 4상태의 제한된 JSON 동작표 실행기 3h / `read_inputs`·`preview_flow`·`run_trial` 및 승인 화면 3h / 실물 시험 3h. 서보 덮개 1개와 센서 2종으로 한정하고 범용 펌웨어 생성은 하지 않는다.
- **90초 시연:** 0~35초 요구 입력·확인 질문·승인 → 35~55초 가림/접근에 따른 덮개 동작 → 55~90초 “버튼도 눌러야 열리게”로 변경·재승인·같은 자극에서 달라진 반응. 명령 ACK를 실제 동작 성공으로 표시하지 않는다.
- **SDG 하나:** **4.4**, 학생의 디지털·기술 실습 역량. 교육 효과를 검증했다는 주장은 하지 않는다.
- **가장 큰 위험:** 미리 만든 메뉴를 말로 고르는 데모로 끝나는 것. 사전 등록하지 않은 복합 요구 1건을 처리하고, 지원 밖 요구는 거절해야 차별성이 생긴다. 상태도 편집 GUI는 만들지 않는다.

### ② AI 고장 탐정 — 매뉴얼을 읽고 실험하는 능동 점검대
- **트렌드 근거:** T3의 제조 점검과 T6의 실행·관찰·수정 흐름. 경보를 띄우는 것이 아니라 다음 점검을 골라 원인 후보를 좁힌다. 대상은 학교 메이커실의 실습 장치다.
- **피코의 필요성:** 서보 셔터를 짧게 시험 구동하고 거리·조도 변화를 측정한다. 제어 명령을 보냈다는 사실과 실제 장치가 움직였다는 증거를 분리한다.
- **LLM의 필요성:** 자유로운 고장 설명·기종별 매뉴얼·정비 메모를 함께 읽고 확인 질문과 검사 순서를 정한다. 센서값만 보고 정해진 고장명을 붙이는 분류에는 쓰지 않는다.
- **12시간 MVP:** 셔터·센서 3h / 서로 다른 실습 매뉴얼 2종과 측정·구동 도구 3h / 근거 인용·승인·재검사 화면 3h / 고장 주입 시연 3h. 물리적 수리는 사람이 하고 AI는 원인 후보와 다음 검사만 제안한다.
- **90초 시연:** “모터가 고장 났다” 입력 → 근거를 읽고 시험 제안·승인 → 셔터 이동은 관측되나 빛은 그대로임을 확인 → 광경로 점검 요청 → 사람이 센서 앞 가림판 제거 → 재측정. 즉시 ‘모터 불량’이라고 단정하지 않는 장면이 핵심이다.
- **SDG 하나:** **9.5**, 설비 점검을 통한 기술 실험·연구 역량 강화.
- **가장 큰 위험:** 고장 2개를 외운 분기표가 LLM보다 낫다는 반론. 새로운 정비 메모·상충 설명에서도 검사 계획을 바꾸는지 확인해야 하며, 실제 산업 설비 진단 성능은 주장하지 않는다.

### ③ AI 무대감독 — 대본을 조명과 장치 동작으로
- **트렌드 근거:** T5의 언어 기반 IoT 제어와 T7의 표현형 로봇을 학생 창작 도구에 적용한다.[추정] ‘AI 무대감독이 수상작 유행’이라는 뜻은 아니다.
- **피코의 필요성:** 지정 무대 지점의 점유·진행 버튼을 읽고 LED 조명과 서보 종이막을 움직인다. AI는 연출 계획을 만들고 실제 큐 실행·중지는 Pico가 맡는다.
- **LLM의 필요성:** 대본의 장면 전환·상대적 순서·연출 수정 요구를 실행 가능한 큐로 바꾸고 모호함을 질문한다. 이미 정해진 타임라인 재생에는 LLM이 필요 없다.
- **12시간 MVP:** 종이무대·막·LED 3h / 점유·버튼·타이머 큐 실행기 3h / 3장면 텍스트 대본 해석·승인 3h / 리허설 3h. 음성 인식·배우 식별·음원 생성은 제외한다.
- **90초 시연:** 짧은 대본 입력·연출 확인 → 승인 → 모형 배우를 감지 지점에 놓아 조명·막 실행 → “엔딩은 암전 없이 막만 내려”로 현장 수정·승인 → 바뀐 결말 재생. 텍스트와 무대의 차이를 즉시 보여준다.
- **SDG 하나:** **4.4**, 학생 공연팀의 디지털 창작·장치 제어 기술 습득.
- **가장 큰 위험:** 공연 전체를 이해·추적하는 시스템으로 범위가 커지는 것. 초음파는 한 지점의 점유만 확인하며, 대사 이해나 배우 위치 추적을 했다고 주장하지 않는다.

## 4. 최종 순위와 채택 기준
- **1순위 ① Pico Forge → 2순위 ② AI 고장 탐정 → 3순위 ③ AI 무대감독.** ①은 하드웨어 바이브코딩이라는 직접적인 최신 선행 사례가 있고, 자유문장의 가변성과 실물 검증을 모두 과제의 중심에 놓는다.[추정]
- ①의 발표 핵심은 **“코드를 써주는 AI를 넘어, 내가 말한 조건대로 현실에서 움직였는지 확인하는 AI”**다. SDG는 마지막에 기술교육 효과로 연결한다. ②는 규칙표 대비 이득, ③은 고정 연출 대비 이득을 증명하기가 더 어렵다.[추정]
- 채택 검증 기준: 미등록 요구 처리·모호함 질문·지원 밖 동작 거절·실제 센서 기록과 결과 대조·승인 전 미구동·통신 단절 시 안전 정지. 고정 메뉴 대비 요구 수정의 수고가 줄지 않으면 LLM 이득을 입증하지 못한 것이다.
- **검증 범위:** 링크 원문과 수상 보도를 조사했다. Command Code API는 호출하지 않았고, 후보의 하드웨어·성공률·시연 지연은 실행 검증하지 않았다. 소스 조사 결과와 제작 제안을 혼동하지 않는다.
