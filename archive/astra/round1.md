# GPT 측 1라운드 제안서

## 1. 결론과 우선순위

**첫 선택은 「통학로·횡단보도 앞 장기 점유 알림」이다.** 이번 조사에서 확인한 2025년 12월 수원시 국민신문고 유형에서는 주정차가 가장 컸고, 장난감 차량·초음파 센서·표지판으로 문제와 대응을 같은 자리에서 보여줄 수 있다.[S4] 두 번째는 「공동 배출장소 넘침·방치 알림」이다. 두 안 모두 카메라 없이 만들되, 위반자를 판정하거나 자동 신고하지 않는다.

한 팀이 아래 다섯 작품을 모두 만드는 계획이 아니다. **2~3인 팀이 하나를 골라 실제 제작 약 12시간 안에 완성하는 다섯 후보**다. 상대 측 제안은 참조하지 않았다.

| 순위 | 아이디어 | 민원 근거 강도 | 구현 가능성 | 피지컬 AI 완성도 | 시연 임팩트 | SDG 적합성 | 합계 /25 |
|---|---|---:|---:|---:|---:|---:|---:|
| 1 | 통학로·횡단보도 앞 장기 점유 알림 | 3 | 5 | 4 | 5 | 5 | 22 |
| 2 | 공동 배출장소 넘침·방치 알림 | 2 | 5 | 4 | 5 | 5 | 21 |
| 3 | 빗물받이 배수 지연 경보 | 2 | 4 | 4 | 5 | 5 | 20 |
| 4 | 공사장 지속 소음 작업 알림 | 3 | 4 | 4 | 4 | 4 | 19 |
| 5 | 보도·생활도로 요철 점검 카트 | 2 | 3 | 4 | 4 | 5 | 18 |

점수는 실험 성적이 아니라 설계 평가다. 다섯 항목을 같은 비중으로 합산했다. 근거 강도 5점은 **수원시의 동일 생활문제에 관한 비교 가능한 5년 이상 직접 통계**, 3점은 특정 월·구의 직접 수치, 2점은 복합 유형·담당 부서 통계와 현장 사례의 결합으로 정했다. 구현 가능성은 초보자의 12시간 제작, 피지컬 AI는 센서→실제 API 판단→작동→상태 재확인의 연결, 시연은 강당 재현성, SDG는 세부목표와의 직접성을 평가했다.

**근거의 한계부터 명시한다.** 2019~2024년 수원시 공식 민원서류 처리 자료를 확보해 최소 5년 조사 조건을 충족했다. 그러나 이것은 증명서 발급 등을 포함한 광의의 민원이다. 다섯 생활문제 각각의 2020~2024년 연속 신고 건수는 확보하지 못했다. 따라서 아래 순위를 ‘5년간 생활민원 상위 5종’이라고 부르지 않는다. 장기 행정통계, 부서별 접수 원자료, 특정 기간의 직접 생활민원 근거를 구분해 후보를 선정했다.

## 2. 직접 확인한 민원 데이터와 해석

### 2.1. 공식 연보: 2019~2024년, 6개년

- **연도별 추이:** 총계는 2020→2021년 증가, 2022년 감소, 2023년 증가, 2024년 감소다. 2020년 대비 2024년은 4.25% 감소했다. 원문값으로 계산한 결과이며 생활불편의 감소율은 아니다.[S1]
- **상위 유형:** 2024년 확인·증명/교부가 총계의 93.75%를 차지한다. ‘민원 대부분이 생활환경 불만’이라는 해석은 틀리다.[S1]
- **고충민원의 범위:** 연보의 2024년 고충민원 297건을 국민신문고 전체 접수량으로 사용할 수 없다. 채널·처리단계·분류가 다르다.[S1]
- 증감의 원인을 코로나19, 정책 효과, 시민 만족도 변화라고 단정하지 않는다. 이 표만으로는 원인을 식별할 수 없다.
- 2025년 연간 민원서류 처리값은 확보하지 못했다. 연보 발행연도와 통계 기준연도를 구분했다.

### 2.2. 공공데이터포털 CSV: 5년 이상 읽었지만 품질 이상 발견

`경기도 수원시_민원접수통계현황_20251104`를 다운로드했다. CP949로 열었으며 **1,765행, 기준년도 2015~2025**, 열은 `기준년도, 시군구명, 주관 부서, 민원접수건수, 데이터기준일자`다.[S3]

1. 2023년과 2024년은 총계만 같은 것이 아니라 **165개 부서의 이름·건수 쌍 전체가 동일**하다. 원문 중복 가능성이 있어 두 해를 독립 관측치로 신뢰하지 않았다.[S3]

4. 2025년 행은 데이터 기준일이 2025-11-04여서 완결된 연간 실적으로 간주하지 않았다.[S3]

숫자 자체는 파일에서 확인한 **원문값**이며 추정으로 채운 값이 아니다. 다만 집계 기간·채널의 일관성과 중복 원인은 미확인이다. 연보와 CSV도 서로 다른 통계이므로 합산하거나 서로의 결측치를 메우는 데 쓰지 않는다.

동일 기사에서 2024년 12월 전체는 **23,736건**, 2025년 12월은 **27,521건**으로 확인된다. 같은 달끼리 계산하면 15.95% 증가지만, 이를 연간 증가율로 바꾸지 않는다.[S4] 기사에는 분야별 분류도 별도로 나오므로 위 유형표와 분야표를 다시 합산하지 않는다.

신고 빈도도 피해 인구와 같지 않다. 기사상 2025년 12월 **25명이 접수한 4,756건**이 전체의 약 17%다. 반복 신고·참여 편중을 감안해야 한다.[S4]

## 3. 다섯 안의 공통 구현·API 계약

### 3.1. 피코는 감지·작동, 노트북은 API 중계

```text
센서 → Pico WH / MicroPython
     → USB 직렬(JSON Lines, 1초당 상태 요약)
     → 노트북 Python 중계 + 로컬 웹 대시보드
     → 휴대폰 핫스팟 → HTTPS Command Code Provider
     → 검증된 확률·동작 코드 → USB 직렬 → LED·부저·서보 표지
```

**노트북 중계를 선택하고, MVP의 피코↔노트북 구간은 USB로 고정한다.** Wi-Fi가 탑재됐다고 반드시 무선으로 연결할 필요는 없다. 이 선택은 피코의 TLS 메모리·인증서 검증·API 키 저장 문제와 핫스팟의 단말 간 통신 차단을 함께 피한다. 피코 자체가 `urequests`로 외부 HTTPS를 호출하지 않는다.

- 인터넷은 팀의 휴대폰 핫스팟을 전제로 한다. 피코를 직접 Wi-Fi에 연결하는 확장에서는 2.4GHz만 가능하고 캡티브 포털을 처리하지 못한다는 조건을 유지한다. **무선 확장은 12시간 MVP에서 제외**한다.
- 노트북의 `CMD_API_KEY` 환경변수에서만 키를 읽는다. 코드·피코·브라우저·CSV·스크린샷에 키를 넣지 않고, 노트북의 HTTPS 인증서 검증을 끄지 않는다.
- 중계는 센서 수신과 외부 요청을 분리한다. 외부 호출 중에도 직렬 수신·로컬 화면·피코 샘플링이 계속되어야 한다. 기기당 동시 API 요청은 하나이며 대기 중 새 상태는 최신 요약 하나로 교체한다.
- 노트북 화면은 원시 지표, 최근 창 요약, 모델 확률, 선택 동작, 호출 지연, `ONLINE / PENDING / OFFLINE / SENSOR_ERROR`를 표시한다. 서버와 대시보드는 노트북 로컬에서만 연다.
- USB 포트는 중계 프로그램 하나만 연다. 시연 때 Thonny 등의 직렬 모니터를 닫고, 충전 전용이 아닌 데이터 USB 케이블을 쓴다.
- 시민의 얼굴·번호판·음성·민원 원문·정확한 집 주소를 보내지 않는다. 모델 입력은 센서 요약과 부스 설정뿐이다. 제안서의 민원 통계는 문제 선정 근거이지 모델 학습 데이터라고 주장하지 않는다.

### 3.2. 엔드포인트와 실제 문서의 스키마

다섯 안 모두 다음 계약을 사용한다.[A1]

```text
Base URL: https://api.commandcode.ai/provider/v1
POST /systemone
Authorization: Bearer <CMD_API_KEY>
Content-Type: application/json
model: typesafe/jev
```

`typesafe/jev`는 텍스트 생성 모델이 아니다. `state`는 텍스트로 보내고, 이름 있는 `questions`에 `noul`, `choice`, `score`를 정의하면 `answers`로 확률·선택·점수가 돌아온다. 한 요청에 관련 질문을 묶으며 공식 한도는 100개다.[A1] 각 안의 JSON 입력은 **설명용 가상 센서값**이며 실측이나 API 실행 결과가 아니다.

예를 들어 1번 안의 상태 요약을 `state` 문자열로 직렬화하고, 아래처럼 요청한다. 뒤의 안별 `questions` 객체로 교체하면 같은 중계를 재사용할 수 있다.

```json
{
  "model": "typesafe/jev",
  "state": "demo=true; zone=marked_crosswalk_approach; occupied_s=18; distance_a_cm=7; distance_b_cm=8; transitions_20s=1; maintenance=false; valid_ratio=1.0",
  "questions": {
    "action": {
      "type": "choice",
      "instructions": "표시된 통행 공간의 센서 관측만 평가하라. 차량 종류나 법 위반 여부는 추정하지 말라. 짧은 통과와 지속 점유를 구별하고 관측이 충돌하면 review를 선택하라.",
      "criteria": {
        "clear": "통행 공간이 비어 있음",
        "pass": "잠깐 통과 중이어서 안내를 보류",
        "warn": "통행 공간의 지속 점유로 이동 안내가 필요",
        "review": "센서 충돌이나 정보 부족으로 사람이 확인해야 함"
      }
    }
  }
}
```

실제 문서에 맞춘 응답 읽기 규칙은 다음과 같다. 아래 필드 설명은 출력 계약이며 응답을 받았다는 뜻이 아니다.[A1]

| 질문 종류 | 읽을 필드 | 범위·주의 |
|---|---|---|
| `choice` | `answers.<이름>.choice`, `.confidence`, `.probabilities.<선택지>` | `choice`는 정의한 선택지, 확률은 0~1. 문자열 자유 생성이 아님. |
| `noul` | `answers.<이름>.noul` | 0~1의 예 확률. `yes` 또는 `probability`라는 필드로 잘못 파싱하지 않음. |
| `score` | `answers.<이름>.score`, `.confidence`, `.legend`, `.probabilities` | 순서 있는 기준에 대한 점수. 3단계 기준이면 0~2 범위이며 반드시 정수는 아님. |
| 사용량 | `usage.input_tokens`, `usage.output_tokens` | 실제 이용 시 비용을 재계산하는 근거. |

중계는 질문 키, 허용 선택지, 숫자 범위, 누락값을 검사한 뒤 피코에 짧은 명령만 보낸다. 피코 수신 형식의 예는 다음과 같다. **이것은 팀이 정한 로컬 프로토콜이며 Provider 원응답 형식이 아니다.**

```json
{"seq":42,"mode":"ONLINE","action":"WARN","p":0.86,"ttl_ms":65000}
```

`seq`는 중계가 원요청과 연결해 붙인다. 오래된 요청의 응답으로 현재 상태를 덮어쓰지 않는다. 화면의 확률은 **모델의 판단 확률**이지 ‘실제 사고 발생 확률’이나 검증된 계측 신뢰도는 아니다.

### 3.3. 지연·불확실·오프라인 처리

- 호출 지연은 **[추정] 수백 ms~수 초**로 예산을 잡되 보장값으로 말하지 않는다. HTTP 시간 제한은 5초, 원상태 생성 후 10초가 지난 결과는 폐기한다.
- 판단을 기다리는 동안 파란 상태 LED 또는 `PENDING`을 표시한다. 직전의 유효한 경고는 유지하되, 이미 물체가 사라지는 등 상태가 바뀌면 새 판단을 기다린다. 새 입력 없이 과거 결과를 계속 연장하지 않는다.
- 정기 판단이 30~60초마다 이루어지는 안은 명령 유효기간을 65초로 둔다. **5번 카트는 구간별 일회 결과**라 다음 구간 시작 시 반드시 해제한다. 통신 이상이 확인되면 유효기간이 남아 있어도 `OFFLINE`으로 전환한다.
- `PENDING` 상태에서 위험 여부를 초록으로 확정하지 않는다. 안별 적극 동작은 해당 선택지 확률 0.80 이상일 때만 한다. 경계값·상충 상태는 노란색 ‘확인 필요’로 둔다. 0.80은 **시연용 초기 설정값**으로 현장 성능이 검증된 임계값이 아니다.
- `401/403`은 계정·키 확인이 필요한 상태, `429/5xx`와 시간 초과는 오프라인 대체 동작으로 처리한다. 무한 재시도나 다른 유료 모델로의 자동 전환은 하지 않는다.
- 회선 복구 후에는 과거 요청을 몰아서 보내지 않고 최신 상태로 다시 판단한다. 로컬 필터·타이머·오프라인 기준은 AI가 아니라 전처리·대비 동작으로 구분해 화면에 표시한다.
- 서보는 가벼운 모형 표지판만 움직인다. 실제 도로 차단기·공사 기계·배수 펌프·220V 설비를 제어하지 않는다. 오프라인 안전 신호는 유지하지만 ‘AI가 작동 중’이라고 꾸미지 않는다.

공식 문서상 `typesafe/jev`는 `x-cmd-zdr: 1`을 지원하지 않아 이 헤더를 붙이면 `422`가 난다.[A1] 이를 모르고 개인정보를 넣은 뒤 헤더만 제거하면 안 된다. 이번 설계는 비식별 센서 요약만 전송하고, 개인정보가 필요한 기능을 제외한다.

### 3.4. 하루 호출 수·비용의 공통 계산

시연 하루는 **11/1 오후 3시간 운영**으로 가정했다. 오전 구현·리허설은 아래 비용에 포함하지 않으며, 하루 6시간 계속 가동하면 같은 빈도에서 비용도 약 2배다. 각 요청의 `state`와 모든 질문을 합쳐 **[추정] 입력 800토큰**, Jev의 입력 **$0.042/100만 토큰**, 출력 **$0**로 계산한다. 단가는 공식 모델 목록의 정밀 표기를 사용했다.[A2]

`시연비용(USD) = 호출 수 × 800 ÷ 1,000,000 × 0.042`

| 아이디어 | [추정] 3시간 호출 수 산식 | 입력 토큰 | [추정] 모델 사용료 |
|---|---|---:|---:|
| 1. 통행공간 점유 | 30초 정기 360회 + 상태 전환·시연 120회 = 480회 | 384,000 | $0.016128 |
| 2. 배출장소 적치 | 60초 정기 180회 + 변화·시연 60회 = 240회 | 192,000 | $0.008064 |
| 3. 배수 지연 | 30초 정기 360회 + 물 주입·회복 60회 = 420회 | 336,000 | $0.014112 |
| 4. 공사장 소음 | 30초 정기 360회 + 사건 시작·종료 60회 = 420회 | 336,000 | $0.014112 |
| 5. 요철 카트 | 40번 시연 × 3개 구간 = 120회 | 96,000 | $0.004032 |

정기 호출과 변화 호출이 겹치면 하나로 합치므로 표는 합치기 전의 계획치다. 호출 간격은 기기당 최소 10초로 제한한다. 이 제한을 계속 채우는 3시간 상한은 **1,080회, 입력 800토큰 가정 시 $0.036288/작품**이다. 입력이 2배면 비용도 2배다. 다섯 안을 각각 운영하는 경우의 계획 합계는 **1,680회·$0.056448**지만 한 팀의 제작 목표는 한 작품이다.

이는 **토큰 소모액**이지 가입·충전 비용이 아니다. 공식 Provider 문서에는 $15 크레딧과 $1.01 처리 수수료가 안내되어 있고, Go 플랜은 API 접근 대상이 아니다.[A1] 기존 API 사용권·잔액이 없으면 먼저 사용자 승인을 받아야 한다. 무료 모델도 계정 조건과 공급 여건을 확인해야 하며 무조건 이용 가능하다고 가정하지 않는다. 휴대폰 데이터 비용·노트북 구입비·세금은 위 산식에 포함하지 않았다.

**이번 조사에서는 Command Code API를 실제로 호출하지 않았다.** 문서와 가격표만 읽었다. 응답 정확도·지연·실제 토큰 수·계정 접근 가능성은 미검증이다.

### 3.5. 공통 부품·전기 안전

- 기본 공통 부품: Pico WH 1개, 브레드보드 1개, 점퍼선, 데이터 USB 케이블, LED 또는 RGB LED, LED 전류제한 저항, 버튼. 노트북·휴대폰은 팀 보유품을 사용한다.
- Pico의 RP2040 메모리에서 LLM이나 영상 인식을 돌리지 않는다. 센서의 중앙값·누적시간·간단한 통계만 계산하고, 필요한 판단은 Provider로 보낸다. 3.3V GPIO 등 전기 제약은 제조사 문서와 맞춘다.[H1]
- HC-SR04를 5V로 구동하면 `ECHO`를 GPIO에 직접 연결하지 않는다. 예를 들어 위쪽 2.2kΩ·아래쪽 3.3kΩ 분압은 5V를 약 3.0V로 낮춘다. 모든 아날로그 입력도 3.3V 범위로 제한한다.
- 서보 전원은 GPIO나 피코 3.3V 핀에서 공급하지 않는다. 별도 5V 전원과 공통 GND를 사용하고, 전원 역급전이 생기지 않게 배선한다. 기구가 걸려도 손을 끼우지 않는 작은 종이 표지만 사용한다.
- 아래 가격은 **[추정] 국내 소매 예산**, 배송비 제외이며 판매처 견적을 확인한 가격이 아니다. 키트 실물 목록이 없으므로 ‘포함 예상’과 ‘미포함 때 보충비’를 분리했다. 고가 센서·카메라는 어느 안에도 필요하지 않다.

## 4. 아이디어별 설계

### 4.1. 통학로·횡단보도 앞 장기 점유 알림

**해결할 문제와 근거.** 주정차로 보행 진입부가 가려져도 보행자가 직접 신고하기 전에는 현장 안내가 없다. 2025년 12월 수원시의 주정차 관련 민원은 **19,151건·69.6%**였다.[S4] 장기 자료에서도 4개 구 경제교통과 접수 규모가 2020년 **27,286건**, 2021년 **32,288건**으로 확인되지만 이는 주정차 단독 건수가 아니다.[S3] 통학로만의 신고량이나 사고율은 미확보다.

**SDG.** 목표 11, 세부목표 **11.2**의 안전한 교통과 아동·보행약자 접근성, **11.7**의 안전하고 접근 가능한 공공공간에 연결한다.[U11]

**시스템 구성.** 학교가 관리하는 보행 진입부의 지정 영역을 가정한다. HC-SR04 2개로 서로 다른 지점의 점유·지속시간을 읽고, 버튼으로 시설 점검 상태를 입력한다. RGB LED와 서보 종이 표지가 ‘통행 공간을 비워주세요’를 알린다. USB 중계·대시보드는 3절과 같다. 초음파는 번갈아 쏴 간섭을 줄인다.

**AI 입력과 판단.** 1초 요약에는 두 거리의 중앙값, 각각의 점유시간, 최근 20초 상태 전환 횟수, 유효 측정 비율을 넣는다. 노트북이 지정 영역·점검 모드·시연 여부를 더한다. 3.2절의 `POST /systemone`, `typesafe/jev`, `action` 질문을 그대로 사용한다.

```json
{"demo":true,"zone":"marked_crosswalk_approach","distance_a_cm":7,"distance_b_cm":8,"occupied_s":18,"transitions_20s":1,"maintenance":false,"valid_ratio":1.0}
```

- **출력→작동:** `answers.action.probabilities.warn >= 0.80`이면 빨간 LED와 안내 표지 전개. `clear >= 0.80`인 새 판단이 연속 두 번이고 센서도 비어 있으면 표지를 접는다. `pass`는 안내 보류, `review` 또는 불확실한 값은 노란 확인 표시다.
- AI의 역할은 짧은 통과·지속 점유·점검 상황을 함께 평가하는 것이다. 번호판·차종·주차 자격이나 불법 여부를 판단하지 않는다.
- **지연/오프라인:** 대기 중에는 파란 상태 표시와 기존 경고 유지. 오프라인에는 시연 기준 8초 이상 점유 시 노란 ‘장기 점유 확인’만 표시한다. 8초는 법정 단속 기준이 아니다. 부저는 기본 비활성이다.
- **하루 호출/비용:** [추정] 480회, 입력 384,000토큰, **$0.016128**. 회당 입력 800토큰·출력 무료 기준.[A2]

**12시간 MVP와 제외 기능.** 단일 진입부, 두 거리 센서, 점검 버튼, AI 확률 표시, 서보 표지 하나까지 만든다. 카메라·번호판 인식·과태료·자동 신고·실제 차단봉·거리 지도는 뺀다.

**강당 시연.** 책상 위 도로 모형에서 장난감 차를 잠깐 지나가게 한 뒤 같은 위치에 15초 이상 둔다. 통과와 지속 점유에 대한 AI 결과를 비교하고 표지가 움직이는지 보인다. 차를 치우면 회복을 확인한다. 끝으로 인터넷을 끊어 `OFFLINE`과 로컬 경고를 보여준다. 실제 사람이 걷는 통로는 막지 않는다.

**리스크와 대응.** 사람·차량을 초음파만으로 구별할 수 없으므로 ‘차량 단속기’가 아닌 ‘지정 공간 점유 안내기’로 명명한다. 부스 사람의 반사음은 센서 방향·가림판·거리 중앙값으로 줄인다. 현장 설치에는 관리자 허가와 방수·방진·일사 조건 검증이 필요하다.

**12시간 MVP와 제외 기능.** 상대 소리 크기·진동·시간 요약, API 분류, 작업자 안내, 수동 확인 버튼까지만 만든다. 음성 녹음·음성 인식·음원 위치 추적·법정 소음 측정·자동 공구 전원 차단은 제외한다.

**강당 시연.** 마이크 가까이에서 나무 블록을 한 번 두드리는 조건과 약하게 반복하는 조건을 비교한다. 주변 부스에 피해를 주는 큰 소리나 실제 전동 공구는 쓰지 않는다. 표지 전개를 본 학생이 두드리기를 멈추면 정상으로 돌아오는 고리를 보인다.

**리스크와 대응.** 강당 박수·방송도 크게 잡힌다. 근접 모형·마이크 방향 고정·사전 기준 측정으로 줄이고, 남는 오탐은 그대로 기록한다. 진동이 있다고 공사 소음임을 확정하지 않는다. 실제 현장 도입에는 공인 소음계와 비교 검증이 필요하다.

**부품·추가 비용.** 공통 부품 + 3.3V 대응 아날로그 사운드 모듈 1개, 진동 센서 1개, SG90 1개, 별도 5V 전원, 작은 목재·완충재. 모두 키트에 있으면 전원 보충품 **3,000~5,000원**과 재료 **2,000~4,000원**, 합계 **5,000~9,000원 [추정]**. 마이크 모듈이 없거나 디지털 비교기 출력만 있는 제품이면 아날로그 모듈 **3,000~8,000원 [추정]**을 추가한다.

### 4.5. 보도·생활도로 요철 점검 카트

**해결할 문제와 근거.** 점검자가 반복해서 지나가는 길의 흔들림을 기록하고, 다시 살필 구간을 골라준다. 2025년 12월 수원시 **도로정비·적치물·노점상 복합 민원 1,384건**이 직접 관련 범주지만, 포트홀만의 수치는 아니다.[S4] 수원시의 2023-02-06~03-31 포트홀 안전조치 **812건**, 2022년 같은 기간 **478건**은 별도의 정비 수요 근거다. 이 수치를 신고량으로 바꾸지 않는다.[S7] 2020~2024년 건설 계열 표 역시 간접 근거이며 품질 이상이 있다.[S3]

**SDG.** 목표 11의 **11.2** 안전한 이동과 보행약자 접근성에 연결한다.[U11] 초보자 팀이 실제 차도에서 주행하거나 보행 보조기구를 자동 제어하는 계획이 아니다.

**시스템 구성.** 손으로 미는 작은 카트에 MPU6050 1개와 바닥 표시를 읽는 적외선 반사 센서 1개를 고정한다. 일정 간격의 시작·끝 표시를 통과한 시간을 이용해 구간 평균 속도를 구하고, 같은 구간의 수직 가속도 변화·충격 지속시간·기울기 변화를 요약한다. 결과는 카트가 멈춘 뒤 LED·서보 점검 깃발로 보여준다. USB 케이블은 여유 있게 두되 구간 길이는 책상 크기로 제한한다.

**AI 입력.** 실제 GPS 대신 `segment_id`를 수동 지정한 모형 구간 ID로 사용한다. 초기 정지·평탄 주행으로 기준을 잡는다. 단 한 번 흔들렸다고 포트홀이라고 판정하지 않는다.

```json
{"demo":true,"segment_id":"B","speed_m_s":0.12,"dynamic_accel_peak_g":0.65,"dynamic_accel_rms_g":0.18,"impact_duration_ms":120,"pitch_change_deg":2.0,"repeat_passes":3,"similar_impact_passes":3,"baseline_valid":true}
```

**API 질문.** `POST /systemone`, `model=typesafe/jev`. 두 질문은 같은 상태를 사용하지만 각각 독립적으로 답하므로 중계에서 함께 해석한다.

```json
{
  "surface": {
    "type": "choice",
    "instructions": "보정된 카트의 구간별 요약을 보고 평탄, 완만한 경사, 반복 충격, 판단 불가를 구별하라. 포트홀 깊이 또는 보행자 부상 확률은 추정하지 말라. 속도 차이나 손 흔들림의 가능성을 고려하라.",
    "criteria": {
      "flat": "평탄 기준과 유사",
      "slope": "급격한 충격보다 기울기 변화가 중심",
      "impact": "비슷한 속도의 반복 주행에서 짧은 충격이 반복",
      "review": "속도, 보정 또는 반복 관측이 불충분"
    }
  },
  "priority": {
    "type": "score",
    "instructions": "이 구간을 사람이 재점검할 우선순위를 평가하라. 점수는 보수 필요성 확정이나 실제 위험 등급이 아니다.",
    "criteria": [
      "새 점검 근거가 약함",
      "추가 주행 또는 육안 확인 필요",
      "반복되는 충격이 뚜렷해 먼저 육안 점검"
    ]
  }
}
```

- **출력→작동:** `answers.surface.probabilities.impact >= 0.80`이면서 `answers.priority.score >= 1.5`이면 빨간 ‘먼저 점검’ 깃발. `review` 또는 나머지 의심 상태는 노란색. 유효한 `flat >= 0.80`만 초록으로 표시한다. 숫자를 도로 관리의 법정 등급으로 쓰지 않는다.
- **지연/오프라인:** 결과를 기다릴 때 카트를 멈추고 구간 ID를 고정한다. 다른 구간으로 이동하면 이전 요청의 결과를 그 구간에 붙이지 않는다. 오프라인에는 큰 충격 이벤트만 저장하고 노란 표시를 낸다. AI 분류·우선순위를 만들지 않는다.
- **하루 호출/비용:** [추정] 40회 시연×3구간=120회, 입력 96,000토큰, **$0.004032**.[A2]

**12시간 MVP와 제외 기능.** 손수레 한 대, 평탄·경사·요철 모형, 구간별 최대 3회 반복 측정, 점검 표지까지만 만든다. 자율주행·GPS 지도·카메라·도로 자동 신고·깊이 측정·자동 보수는 제외한다. 기계 제작이 추가돼 다섯 안 중 초보자 완성 위험이 가장 크다.

**강당 시연.** 같은 길이의 평탄판·완만한 경사판·작은 단차판을 비슷한 속도로 민다. 빠르게 흔들어 한 번 만든 충격과 같은 위치에서 반복되는 충격을 비교한다. 센서 파형이 아니라 ‘다시 확인할 구간을 고르는 결과’와 깃발을 함께 보여준다. 실제 차량·휠체어·학생 탑승은 하지 않는다.

**리스크와 대응.** 속도·바퀴 크기·고정 상태가 신호에 큰 영향을 준다. 카트와 바퀴를 고정하고 광학 표식으로 속도를 비교한다. 손 흔들림·경사·바퀴 접합부를 포트홀로 오인할 수 있으므로 ‘요철 점검 후보’로만 표시한다. 실제 도로의 탐지율은 이 모형 실험으로 입증되지 않는다.

**부품·추가 비용.** 공통 부품 + MPU6050 1개, 적외선 반사 센서 1개, SG90 1개, 별도 5V 전원, 소형 카트·바퀴·모형판. 센서·서보가 키트에 있으면 카트 재료 **5,000~10,000원**, 판재 **3,000~5,000원**, 전원 보충품 **3,000~5,000원**, 합계 **11,000~20,000원 [추정]**. MPU6050이 없으면 **3,000~6,000원**, 적외선 센서가 없으면 **1,000~3,000원 [추정]** 추가다.

## 5. 12시간 제작 배분과 완료 판정

행사 일정 중 기초교육과 전시는 제작시간으로 부풀리지 않는다. 10/31 약 9시간, 11/1 오전 약 3시간의 합계 12시간으로 계획한다. 실제 휴식·정리시간을 고려해 마지막 1시간은 수정 여유로 남긴다.

| 누적 제작시간 | 작업 | 눈으로 확인할 산출물 |
|---|---|---|
| 0~2시간 | 부품 확인·전압 확인·센서 배선·기준 보정 | 실제 입력을 바꾸면 센서 요약이 바뀜 |
| 2~4시간 | USB 직렬·중계·로컬 화면·액추에이터 수동 점검 | 물리 입력→화면, 수동 명령→LED·서보 연결 확인 |
| 4~6시간 | 사용자 승인 후 실제 Provider 연결·스키마 검증 | 실제 센서 상태에 대한 `answers`와 사용량 확인 |
| 6~8시간 | 안별 판단 연결·시간 초과·오프라인 처리 | API 판단→물리 작동→센서 상태 회복 |
| 8~10시간 | 모형 완성·정상/이상/교란 시연 | 같은 조건 반복 시 결과 기록 |
| 10~11시간 | 강당 소음·주변 반사·통신 단절 리허설 | 잘못된 확정 표시와 위험 동작이 없는지 확인 |
| 11~12시간 | 배선 고정·시연 실패 수정·설명판 정리 | 한 작품의 시작부터 복구까지 연속 시연 |

2인 팀은 한 명이 센서·기구·안전을, 다른 한 명이 중계·API·화면을 맡고 4시간째부터 합친다. 3인 팀은 세 번째가 데이터 설명·반복 시연 기록을 담당한다. 실제 API 사용 승인이 없으면 API 판단까지 검증한 작품이라고 발표할 수 없다.

**완료 판정은 기능 목록이 아니라 다음 시나리오로 한다.**

1. 정상 조건, 목표 이상 조건, 헷갈리는 교란 조건을 각각 5회 재현하고 혼동 결과를 기록한다. 정확도 목표를 달성했다고 미리 쓰지 않는다.
2. 원시 센서 요약→요청 상태→실제 응답 확률→액추에이터 변화가 한 화면과 실물에서 연결돼야 한다. 수동 버튼으로 확률을 만들어 넣는 시연은 AI 시연으로 인정하지 않는다.
3. 인터넷 단절·5초 시간 초과·센서 분리 시 `OFFLINE` 또는 `SENSOR_ERROR`가 분명히 드러나고 안전한 동작으로 전환돼야 한다.
4. 상태가 바뀐 뒤 늦게 도착한 응답이 이전 경고를 새 구간·새 대상에 적용하지 않아야 한다.
5. 같은 센서 요약에 단순 임계값 기준도 별도로 적용해 오탐·미탐을 비교한다. AI가 더 낫다는 주장은 실제 비교가 뒷받침할 때만 한다. 비교용 규칙을 온라인 AI의 대체 본체로 숨기지 않는다.

이 제안 단계에서 한 일은 **문서 조사, 파일 열람·집계, 비용 산식과 요청 구조의 검토**다. 실물 센서, 회선, Provider 응답, 현장 탐지 성능은 아직 실행 검증하지 않았다.

## 6. 이 과제에서 빠지기 쉬운 함정 5개

1. **서로 다른 숫자를 같은 민원으로 취급한다.** 연보의 확인·증명/교부, 부서별 접수, 국민신문고 신고, 안전조치 실적, 시설 수를 섞으면 문제 크기가 부풀려진다. 특히 2025년 12월 쓰레기·충전구역의 복합 수치를 쓰레기 단독으로, 자동차 등화장치를 가로등으로 바꾸면 안 된다.[S1][S3][S4][S7]
2. **파일이 공식이라고 품질 확인을 생략한다.** 공공데이터 CSV의 2023·2024년 부서별 값이 전부 같은 것을 ‘민원이 정체됐다’고 해석하지 않는다. 부분연도·중복 가능성·조직개편을 표시하고, 없는 연도는 미확보로 남긴다.[S3]
3. **피코의 처리능력과 AI의 관측능력을 과장한다.** RP2040에서 LLM·카메라 비전을 돌리지 않는다. 초음파는 법 위반을, 마이크 ADC는 공인 dB(A)를, 수위 센서는 침수 원인을, MPU6050은 포트홀 깊이를 알려주지 않는다. AI도 입력에 없는 사실을 만들어낼 수 없다.
4. **API 성공만 가정하거나 가격을 토큰값만으로 설명한다.** 키·요금제·초기 충전·ZDR 미지원·5초 지연·회선 단절을 고려한다. 제안서에는 호출하지 않은 값을 실측처럼 쓰지 않는다. 오프라인 규칙 시연을 실제 API 판단으로 포장하지 않는다.[A1][A2]
5. **강당에서 재현 불가능하거나 위험한 작품을 고른다.** 실제 악취·연기·큰 공사 소음·도로 주행·220V 릴레이·사람을 막는 차단기는 쓰지 않는다. 모형에서 확인한 결과를 도시 전체 민원 감소 효과로 확대하지 않는다. 알림 이후 누가 수거·이동·점검할지도 시연에 포함한다.
